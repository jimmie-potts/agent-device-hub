# Device MCP module 1.0.0

This private package embeds authenticated MCP in an owning application's optional local HTTP route. It exposes registered services through common status, power and brightness tools or strict application-specific extensions. It does not listen, scan the LAN, start playback or write to devices.

Use Node 24. The protocol matrix is MCP 2025-11-25 and 2025-06-18 with `@modelcontextprotocol/sdk` 1.30.0, pinned in the lockfile. The shipped SDK has an MIT license, retained in SDK-LICENSE. Zod 4.5.4 and Ajv 8.20.0 are MIT dependencies whose installed packages carry their notices. This is the maintained initialization-based SDK line. The current SDK v2 uses a different HTTP protocol and is not claimed as compatible here. [Official SDK](https://github.com/modelcontextprotocol/typescript-sdk), [selected transport specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

## Embed the module

Create an immutable registry with server-configured controller/device IDs. `createDeviceTools(registry)` exposes generic tools using explicit registered device IDs. `bindDeviceTools(registry, {deviceId, prefix})` fixes the device in server configuration and emits `<prefix>_status`, `<prefix>_power_set` and `<prefix>_brightness_set`. Setters take `requestId`, `expectedConfigurationRevision`, `expectedGeneration` and either `on` or `percent`.

A shared `ControllerService` implements `readSnapshot(context)` and `submit(request, context)`. It owns atomic admission, request replay, revisions, generations and physical serialization. Context carries current machine authorization facts and the principal ID. It has no bearer token or MCP cancellation signal. The module validates and preserves API 1.0 snapshots and receipts, including unknown observation, queued intent and priorEffects.

`createMcpHandler({enabled, registry, tools, authenticate, allowedHosts, allowedOrigins, limits?})` returns `handle(req,res)` and `close()`. Mount the handler before a body parser on the owner's explicit `/mcp` route. The host owns the listener and request/header limits before dispatch. Start with loopback only; any same-machine Windows/WSL route is explicit deployment configuration. Controller access to its configured LAN hardware remains with the controller. No broad listener, tunnel, proxy configuration or personal setup occurs in this package.

The asynchronous `authenticate(token, signal)` callback returns `{id, credential:{kind:'machine',status:'active'|'overlap',declared:true,devices,scopes}}` or null. It must use an independently provisioned machine credential, never a browser edit token. Unknown/revoked credentials return null. Declare overlap only during an intentional rotation interval. Verify every request against current credential state; never pass incoming credentials through to a remote controller. The module verifies Host and every supplied Origin using exact allowlists, rejects cross-site Fetch-Metadata, and can apply a stricter `allowFetchMetadata` callback. Absent Origin does not authenticate a request.

Initialization creates a random session bound to the principal. Every request authenticates again, including discovery and replay. Discovery includes only tools allowed by the current device list and scope; generic target enums contain only those authorized devices. POST responses use JSON; GET streams return 405. DELETE ends only the MCP session. No SSE event store, agent tools, prompts, sampling or task execution is advertised.

## Existing application extensions

A registration may contain `extensions` without a shared `service`. This supports Pixoo's existing `request_id` and player/catalog APIs while its generic machine API remains separately scoped. An extension declares strict object `inputSchema`, object `outputSchema`, read/control `scope`, accurate annotations, a bounded description and `invoke(args,context)`. It receives a fixed registered target through context. Input schemas cannot expose raw target/credential override fields. The owning application must validate its device-specific IDs and apply its existing replay/queue rules.

`bindServiceTools(registry, {deviceId, bindings:[{extension,name}]})` maps registered extensions to names such as `get_status`, `set_screen`, `list_media` or `play_playlist`. Results contain `{kind:'extension',data}` with matching JSON text. The published output schema embeds the extension as a JSON Schema resource, so its local `$ref` and `$defs` resolve against the extension root. These results do not fabricate shared snapshots or receipts, so an extension tool's published output schema allows only `extension` or `gateway-error` results. Every published input and output schema keeps only the shared contract definitions it references, which keeps the tool catalog within the response limit as devices are added (Hub #357). Thrown write calls return possible prior effects and preserve a bounded `request_id` when present. Extensions return their own schema-valid domain failures with `isError:true`; no automatic retry or new request ID is created. See examples/consumers.ts for both consumer forms.

Generic tools require a shared service and their target schema excludes extension-only registrations. No extension changes the controller API 1.0 schema. All externally reachable calls still use the registered target, current scopes, common transport limits and response validation.

## Limits and recovery

Defaults are 64 KiB request JSON, 1 MiB response JSON, 32 outstanding HTTP operations and 32 outstanding controller calls, 16 sessions, 64 devices, one second for authentication, ten seconds for request/body waiting and five minutes of session inactivity. Tool definitions must fit the response limit at construction. The response limit includes the complete serialized JSON-RPC envelope and escaped request ID. IDs that leave no room for a failure response reject before dispatch. Input and controller data use a conservative bounded JSON walk before serialization. Controller Snapshot.limits describes the owner and is not overwritten with MCP transport limits.

A timed-out verifier or controller still occupies its operation slot until it settles, even if it ignores cancellation. Later requests fail at capacity. This bounds detached work. Hosts should make their own verifier/controller dependencies settle within known limits. Limits can be lowered through `limits`; invalid/nonfinite settings reject construction. Request bodies cannot exceed the API's 64 KiB maximum.

An internal adapter repairs two JSON transport lifecycle defects in SDK 1.30.0. It resolves pending delivery with HTTP 204 on cancellation or closure and removes completed JSON streams. The public `closeSSEStream` method cannot clean successful JSON responses after the SDK removes their request mapping, so the adapter uses the pinned internal stream maps and cleanup callback. Dependency upgrades must recheck that layout and run the lifecycle and retained-stream tests. Controller operation slots remain occupied until the owning call settles.

Explicit cancellation before dispatch prevents submission. Once dispatched, the controller owns the work. Disconnect, DELETE, idle expiry, credential revocation and `close()` stop MCP delivery or new admission without stopping backend playback. A timeout or invalid response after a write may have effects. The result reports that uncertainty, retains the request identity and never invents receipt revisions. Read a current snapshot or explicitly replay the exact original identity through the owner. Never automatically replace an ambiguous request with a new identity.

Read hints are readOnly=true, destructive=false, idempotent=true. Common write hints are readOnly=false, destructive=true, idempotent=false. All use openWorld=true because registered services can reach devices. Annotations never grant permission. Queued/sent outcomes do not prove visible hardware state or agent task success.
