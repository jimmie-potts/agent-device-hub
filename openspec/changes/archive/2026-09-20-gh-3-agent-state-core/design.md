## Context

See proposal.md for scope and motivation. Lifecycle 1.0 supplies strict envelope validation and content/native retry keys. There is no existing state runtime or host storage API. The issue's host is supplied later by Pixoo #31. Design is required because this change introduces concurrent state, persistence, privacy, timing and migration behavior.

## Goals / Non-Goals

Provide one embeddable owner with a portable persistence contract and isolated consumers. Keep all stored values derived from validated metadata. Preserve explicit uncertainty for source capabilities not established by the provider matrix.

No installed hooks, production listeners, device writes, personal state migration, provider read writes or frontend features are included. The source API does not claim that a host has implemented its storage contract or that installed client/physical qualification passed.

## Decisions

1. Use a required host storage adapter with an exclusive lease, versioned load and atomic revision-checked commit. Keep journal and current records logically separate. Host adapters implement atomicity and durable I/O; an exported in-memory reference adapter provides executable conformance examples and failure injection for source tests. A process-local cache alone is insufficient for production hosting. Publish only after commit. On ambiguous failure fault the owner until shutdown/reload; never retry a possibly committed mutation.
2. Serialize accepted mutations through a finite admission queue. Reduce one session at a time using an injected clock. Bound sessions, attention, notices, source-order records and retry keys; reject new work at capacity with loss evidence instead of evicting durable notices. Storage receives bounded incremental changes so a full journal is not serialized for every admission. Retention runs on admission, startup, an idle timer and explicit maintenance. The journal read projection excludes expired rows even before the next storage commit.
3. Retain independent attention entries and consumer-scoped notice acknowledgments. Stable notice identity derives from session/turn evidence and transition identity. Retired known turns and per-dimension sequence watermarks prevent stale resurrection. A newer attention observation does not discard an independently reordered activity observation for the same turn. Conflicting native retry content has a separate fingerprint in the bounded retry set. Unknown ordering remains visible; contradictory or uncorrelated evidence cannot clear known state. A new turn retires the previous turn's monitor notices only when the transition is established; ambiguous turns require acknowledgment or later evidence. No observation means successful work or provider readership.
4. Snapshot objects are detached and immutable. The durable revision identifies stored content; query time, observation age and freshness are explicit projection context. Collector health never changes last session evidence. Restart sets a separate uncertainty condition cleared only by fresh accepted lifecycle evidence. Parent aggregation derives from unique evidenced child selectors and freshness, never from counters incremented by events.
5. Registered consumers pull bounded revision notifications through independent async iterators. Overflow replaces that consumer's backlog with a resync marker and a saturated loss count. Snapshots are fetched separately, so large current state is not repeatedly queued. Historical notifications are state invalidations, never device commands or replayable effects.
6. Consume `docs/performance/linux-budgets.json` from merged #77 unchanged: 3,000 ms producer hard deadline, 2 KiB normalized events, 128 pending events and 256 KiB per consumer, 128 MiB future service RSS constraint, with 1/10/50 p95/p99 ceilings 63/65, 82/87 and 377/396 ms. Hook source stays small and separate from reducer/schema initialization. Integrated service/consumer and matched end-to-end qualification remain #30; finite queue, timeout and failure behaviors are checked here.
7. Provider normalizers select documented IDs and event kinds from raw JSON. They generate one observation timestamp, use unknown ordering and preserve metadata on a retry by reusing the normalized envelope. Do not infer native event IDs, provider occurrence time, approval correlation or input semantics. Raw provider input is never logged. Installed activation requires explicit qualified source configuration and remains #8; source tests use synthetic configuration and transports.
8. Version the package, durable export and snapshot schema separately from lifecycle 1.0. Supply a pure Python snapshot validator using the same corpus, with no Python reducer. Bundle the verified lifecycle 1.0 archive in reproducible packaging, check manifests and external imports, and publish immutable release artifacts after source delivery.

## Risks / Trade-offs

- A host can violate atomicity or lease ownership. Document its mandatory conformance suite and verify competing owners, failed and ambiguous commits, restart and import with the reference adapter; actual Pixoo storage adoption is #31.
- Provider order is usually unknown. Preserve uncertainty and conservative notice/attention behavior instead of presenting receipt order as evidence.
- Retained undismissed state can fill finite capacity. Reject admissions and surface loss/capacity explicitly; journal cleanup never silently makes room by deleting that state.
- JavaScript timers cannot preempt a blocked host event loop. The standalone hook has a process deadline; embedded hosts must preserve event-loop responsiveness and use cancellable bounded I/O. Integrated qualification checks the real host.
- The existing guide changes as delivery facts change. Update canonical inputs and generated HTML, validate it and obtain current-candidate human approval where repository UI rules apply. Public publication remains separately authorized.

## Migration Plan

Ship a private source artifact without installing it. An embedding host acquires its exclusive storage lease, validates stored format and starts the owner. Shutdown drains or faults bounded work and releases the lease. Export first quiesces new writes and captures a consistent versioned state. Import requires an empty exclusive destination and preserves revision/source/session/notice identities. The old owner stays stopped until explicit rollback; never use the same live database across processes or operating systems. Unsupported versions fail with fixed codes and preserve the source export.
