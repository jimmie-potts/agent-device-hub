## Context

See proposal.md for why. Before this change `AssistantEngine.#input` refused a start with `capacity` while the conversation's task was unfinished, and nothing waited for a task to end. Each conversation has its own running slot and change revision (#2027), New conversation moves a profile to a fresh conversation (#2029), a coding hand-off can wait for its companion's worker slot (#2028), the title model checks the title after each finished task and never at a start (#2075), and knowledge commands are checked per scope (#2056).

## Goals / Non-Goals

**Goals:** a durable per-conversation queue the owner can add to, edit, withdraw from and reorder; each queued message started as a new task and turn when the task before it ends; Stop and restart holds released by the owner; at-most-once starts across crashes; additive contract minors; a page that keeps the composer available while a task works.

**Non-Goals:** steering a running task, Skip question and send, Decline with message, and returning unread steers on Stop (#2031); a separate explicit hold control; holding the queue after a failed task; any change to `assistant-input`.

## Decisions

1. **One queue per conversation, a module table.** `assistant_queued_messages` holds each message with its conversation, profile, position, text, times and the queuing command's trace; `assistant_queues` holds the queue's revision and hold. It follows Codex's `queued_items` table (Apache-2.0) and sits beside the checkpointer, since LangGraph's double-texting strategies belong to the LangSmith server. Queues are keyed by conversation because tasks are (#2027). New conversation is refused while a queue holds messages, as for an unfinished task, so a queue never outlives its conversation's current status.
2. **The message is domain state, not a command.** Queue is a staged input, `{action: 'queue', profile, text, expectedRevision}`, whose command completes once the message is saved (ADR 0012). Its ID is that command's request ID; the shared receipt table already acknowledges a repeated request, so a repeat queues nothing, before or after the start.
3. **Dispatch in the commit that ends the task.** `#change` saves a task's terminal transition, then `#dispatch` starts the queue's head when the queue is not held and the conversation has no unfinished task: it creates the task with its prompt message, activates its run and deletes the queued row in the same transaction, then publishes. The session report therefore emits the earlier turn's end before the next turn's start, and a crash can never leave the message both started and queued; Codex's `start` deletes after starting and could run it twice. The run launches after the commit; while the earlier run still settles, the launch waits for that run to release the conversation's slot. Queue also dispatches when nothing runs, as Codex dispatches after an enqueue.
4. **Holds.** Stop (`cancel`) sets the `stop` hold when messages are queued; a start sets the `restart` hold on every queue that still holds messages and was free, and publishes it at a new revision; a refused start sets `refused` with the refusal's code and fixed reason, such as the spend limits' `capacity` message. `resume-queue` releases any hold and dispatches; a start it cannot make refuses the command, so the hold stays and nothing retries. The page names it **Start** after a restart and **Resume queue** otherwise. A queue left empty is released. This follows Codex's interrupt rule and T3 Code's `queueHeld`.
5. **A queue revision scope.** Queue commands name the assistant revision read and are stale only when the conversation's queue changed after it, as #2056 checks knowledge scopes. Checking against the conversation's change revision would refuse an edit after any step of the running task. Each start raises every saved conversation's queue revision to the start's, and after reconciliation to its conversation's change revision; New conversation counts both queues as changed; so a Queue naming a revision read before either is refused exactly when a Send is. Changes are marked in a `pending` column inside the transaction, so a rolled-back command records nothing. The queue read names the revision it was read at, and the page's commands on what it shows name that revision, or the revision at which an edit opened.
6. **When a task ends.** Succeeded and failed tasks start the next message, as Codex dispatches on any non-interrupt idle; a cancelled task holds the queue. A task waiting on an answer, an approval or the coding worker, or paused or uncertain, is unfinished, so the queue waits. A queued start meets the same checks as a new message (conversation on, recovered, spend limits) before anything is written, and runs no title check; the finished task's own check covers the conversation.
7. **Contracts by additive minors.** `assistant-control/2.2` adds `withdraw` and `reorder` (with `profile`, `queuedId` and, for a reorder, `beforeId`, null for the end, as T3 Code's `queued-run.reorder`) and `resume-queue` (with `profile`). `assistant-state/2.2` adds `queues`: count, hold and code per waiting queue, no text; the module publishes 2.2 only while a queue holds messages. Editing a queued message is a staged input, because control commands carry no message text.
8. **Steer can land here later (#2031).** A steer that arrives after the last model call becomes the next queued message, and Stop returns unread steers to the queue: both are inserts into the same table, at the head or the tail, inside the transaction that decides them.

9. **Messages an earlier release left behind.** That release's New conversation does not know the queue, so after a return and a roll forward a replaced conversation can still hold queued rows. They never start, are held at each start, stay out of public state, and show on that conversation's read-only view, where Withdraw, the only action, removes them.

## Risks / Trade-offs

- [A failing provider could fail each queued message in turn] → at most 8, each refused or failed with its own closing reply; a refused start holds the queue instead.
- [Send beside a held queue] → Send starts its own task at once and the queue stays held, so the owner's explicit Start still decides when queued messages run.
- [A run that settles while the next starts] → the next run waits for the slot, launched when the earlier run releases it.

## Migration Plan

Both tables are created empty at the first start; no record is rewritten. Returning to the release before ignores them, so messages still queued never start there; withdraw or start them before going back. Prefer fixing forward.
