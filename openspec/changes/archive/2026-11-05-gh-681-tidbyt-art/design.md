## Context

See [proposal.md](proposal.md). This change needs a design because it adds persistent media and crosses command, worker and device-writer boundaries. The current module already owns its SQLite database, writer lease, outbox, tile cadence, serialized queue and Tronbyt moment takeover. The shared art contracts supply bounded input, immutable composition identity, renewal and sender checks.

## Goals / Non-Goals

Deliver exact still and animated compositions with inspectable local evidence and the existing display precedence. Keep the old cloud cards, playback thumbnails and legacy controller compatible. Physical animation, the known manual-pin race and release delays under server holds remain installed acceptance concerns under #687; this source change introduces no device contact or firmware operation.

## Decisions

- **Module-owned media.** Keep a bounded table of 64 staged copies in the existing private database, containing source identity, encoded WebP, decoded frame metadata and expiry. Never evict a valid copy to admit another. Expired staging copies may be reclaimed under their explicit contract lifetime. A moment captures its admitted bytes, so expiry or restaging cannot change it. Reuse `artStageDecision`, `artReferenceRefusal` and `artCommandRefusal`; do not introduce another handoff format.
- **Exact output.** Decode PNG/GIF in a bounded worker using the existing Sharp dependency. Keep the playback PNG path's 64 KiB limit unchanged. The art profile accepts exact 64×32 input up to 160 KiB, at most 20 frames, with animated frame delays from 100 to 800 ms and total duration at most 16 s. Reject metadata mismatches, malformed/trailing input, unsupported animation and oversized output. Flatten transparency onto black after compositing the source frames; preserve every resulting frame and its delay.
- **Owned encoder and narrow mux.** A synthetic three-frame test with two identical frames demonstrated that Sharp's lossless animated encoder reduces `[100, 200, 300]` to two frames with `[300, 300]`. Encode each frame through the existing lossless RGB renderer and wrap those exact full-frame chunks in the [WebP animation container](https://developers.google.com/speed/webp/docs/riff_container). This avoids a native encoder silently changing the declared profile. Independently decode the completed WebP with libwebp through Sharp, including duplicate frames, disposal, transparency, chunk lengths and loop timing.
- **Source-qualified bounds.** [Firmware v1.7.4's graphics loop](https://github.com/tronbyt/firmware-esp32/blob/v1.7.4/main/gfx.c) uses `WebPAnimDecoder` and its timestamps and loops the content for the server's dwell. Its [HTTP buffer configuration](https://github.com/tronbyt/firmware-esp32/blob/v1.7.4/main/Kconfig.projbuild) defaults to 460000 bytes; the Gen 1 defaults do not override it. A 160 KiB output ceiling stays below that source bound. The 20-frame/100–800 ms profile is the module's bounded source profile, not a measured hardware maximum. The current producer's eight 200 ms frames fit it. The 30–60 s takeover remains separate from the animation loop.
- **Atomic local commands.** Staging validates and renders before committing the copy, deduplication receipt and succeeded/observed outcome together. Ambient selection similarly commits selection and its outcome together. These outcomes describe local preparation/selection, never server transmission. Fixed registry refusals precede mutation; storage failures use SDK full-disk classification. Stop cancels preparation and prohibits a later commit. Retained receipts and the existing outbox prevent a duplicate command from causing another effect, including after reopen.
- **Existing effect owners.** Add one reserved ambient installation to the same connection allowlist and one tile to the existing cadence. Its push is always background, including interrupt mode. Attention or a stale sessions copy removes eligible ambient art; a pin or an unknown pin read holds mutations so a manual choice is preserved. The selected composition remains saved while suppressed. Capture target associations so an obsolete queued push cannot reappear after selection, attention or mode changes. Failed or uncertain removal keeps the existing writer's truthful presence and backoff; no selection receipt asserts that removal succeeded.
- **Exact moments.** Admit both moment schema versions, check the sender on moments naming art, and declare `moments.art` only on Tronbyt. Acquire the exact staged copy before admission, then feed its WebP to the existing moment picture seam. No art failure becomes a mood card. The existing control path owns the pin check, foreground push, hold, release, uncertainty and restart cleanup.
- **Private inspection.** Serve stored WebP and bounded preparation/ambient metadata through authenticated module content references. Expose composition identity and transmission evidence, never keys, native installation IDs or server addresses. Keep the existing dashboard card illustrative; the richer browser composition remains the art module's UI input.
- **Synthetic acceptance.** Register a simulation-owned cloud/Tronbyt pair with strict known-URL routing and no real transport fallback. Preserve existing cloud state consumers. Exercise the real gateway, core tracker and module handlers against that route; the simulator's animated readback is checked independently from the encoder.

## Risks / Trade-offs

- The public firmware source establishes decoding and buffer behavior, not optical accuracy or timing on the owner's panel. #687 must verify animation and return to rotation.
- A manual pin can change between a server read and a write; the server has no conditional pin. Art does not add pin writes for ambient content, and the existing moment limitation remains explicit.
- Attention cannot remove art while the queue is held or the server's pin is unknown. Keep presence/effect evidence uncertain and preserve the current writer's recovery rules.
- Persisted media makes the database larger. Bound copies and encoded bytes, refuse capacity without eviction, and test failed writes and reopen with synthetic data.

## Migration Plan

Create additive module-owned tables on open; existing tile/control tables and cloud behavior remain intact. Test an old database, stage/selection reopen, refused commits and duplicate outcomes. #687 assesses this bounded additive storage and verifies the selected installation. Older code ignores the new tables and will not manage the new ambient installation, so an installed recovery must first account for that tile and preserve private state; source checks do not authorize cleanup on the owner's server.
