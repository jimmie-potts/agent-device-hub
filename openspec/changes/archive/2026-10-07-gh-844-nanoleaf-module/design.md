## Goals / Non-Goals

**Goals:** the port as a runtime module with its own store and worker; sync in place of the 1.x feed; commands with replies and outcomes; wall-editor ownership; `device/2.0` with observed power; policy A with one degradation and one recovery per outage; tier 1 and tier 2 scenarios.

**Non-Goals:** the wall and editor pages and the dashboard's power card (#934); the data migration and offline enrollment (#933); module API 1.2 pages, tools and settings (#835); the tracker's handling of late outcomes (#782); moments on Nanoleaf (codex-nanoleaf#158); MCP animation tools (codex-nanoleaf#159).

## Decisions

- **The registry file holds no token.** The port reads its registry from `config.json` in its folder. The module writes it at start from its section, with each device's secret name as `token_ref`, and keeps the tokens it read with `secrets.read` in memory. Each device's link replaces the address and token the port passes, so no credential lives in a module file. Alternative rejected: writing the token into `config.json`, which would copy each secret onto disk outside the runtime's secret checks.
- **The copy of the core's sessions is in memory (`SharedCopy`).** The projection compares each envelope with the previous one, which Python saved in `shared_input.envelope`. ADR 0012 has a module save only its own state, so the previous envelope lives in the module's memory, the column stays NULL, and a restart projects the first sync as a fresh start. The port's recorded trace replay compares the copy's text where it compared the saved one.
- **Sync, not the feed's gap rules.** The SDK resyncs a copy on any gap, so the module projects a completed sync as a resync and each live change as the next local revision, with `lossCount` and `admissionRejected` 0; the projection's own rules for those never fire. A sync's changes are coalesced into one projection after the last of them.
- **Stored commands end at a restart.** ADR 0012: stored intent is responsibility, never a queue. Attempts without a result are uncertain (`recoverAttempts`, which holds a native one), and so is an acknowledgment whose request may have reached the core; queued commands and waiting machine edits fail `cancelled`, and a queued power or brightness command's desired state goes with it. The mode a mode command set stays the module's desired mode, which the worker shows as its own state, not as the command. Comets saved before the restart are dropped.
- **A mode command completes as its mode commits.** A mode is the module's own state: `changeMode` ends the device's queued work, its hold and its overrides, and `desired.mode` shows it at once. So a `device-mode-set` completes `succeeded` with evidence `observed` in its admission's transaction, as the Pixoo module completes its module-local effects (#971). Nothing is sent to the device as part of it, so it has no expiry; the worker's paints follow when the device answers, and availability shows whether it has. Alternative rejected (review of PR #968): journaling it as a device write, which let it fail `expired` while its mode took effect, against ADR 0012's rule that a failure proves no effect. The port's own admission still journals mode commands, as Python did, for the recorded parity tests.
- **Only a write that may have reached the device holds it.** Python also held the device when a queued command expired unsent. That command proves no effect (ADR 0012, "A rejection proves no effect"), and the hold froze the wall with no sign of why (review of PR #968), so `expireQueued` holds nothing; the five recorded cases that showed the hold run as steps. A held device is `degraded` in its record and `held` in its wall view, and the hold is logged once each way. Alternative rejected: keeping the hold for parity, with a flag the module turns off.
- **A device's HTTP error is an answer.** A 4xx or 5xx reply means the device heard the write: the command fails with `transmitted` evidence and the status's code (MAPPING.md receipt rule 3), nothing holds, and the pass starts again without it. A 401 or 403 means the device refuses the module's token, so the device is `degraded`, logged once each way. A failed power or brightness command takes its desired value with it.
- **A failed worker starts again.** A supervisor that ends `locked` or `unrecorded`, as on a busy or full store, or rejects, starts again after a wait that doubles from 1 s to 30 s, with one pending start per device, which a start for a command or a selection replaces; meanwhile the device is `degraded` and its wall view `failing`. The end is logged once, and the recovery once the restarted worker has run for 5 s. A publication whose reads the store refuses is logged once and tried again each second, and a selection's revision bump commits in the selection's own transaction, so no scheduler callback throws (policy A).
- **Machine edits guard on a per-device configuration revision.** Python used the controller ledger's view revision, which is not ported. The revision moves on a wall edit of map settings, elements, a task's project or a project's color, a mode command, an applied machine edit, a favorite edit and a selection of shared input, but not on the palette, Locate, an eviction or session churn, which the issue's rules do not name. One machine edit waits at a time on the Lines, as Python's queue held one; it is processed on a 250 ms local poll while it waits.
- **Outcomes carry their command's trace and family.** The journal keeps neither, so the module records each accepted command's family and `traceparent` in `nanoleaf_commands` in the admission transaction; the report that ends the command reads and deletes the row in the same transaction.
- **Availability.** A link whose last request had no answer is `unavailable`. A device that answers is `degraded` while the module does not present it: it refuses the module's token, its last pass failed (`control_error`, until a successful pass clears it), a hold stops its writes, or no worker runs; otherwise it is `available`. Before any answer it is `unknown`. A request older than one that reached the device does not make it unavailable again.
- **Observed power comes from a poll, and a poll that changed nothing publishes nothing.** The worker reads `/state` only while a saved scene plays, so each device's link is polled with `GET /state` every 5 s while it answers, backing off to 30 s while it does not, and back to 5 s as soon as the device answers any request (Acceptance review of PR #968, round 3: a backed-off read left the observation stale for most of 30 s after the wall came back). The observation moves only when the power or brightness read differs, and `observedAtMs` is the time of the reading that first showed them, as the playback and LIFX records keep it; consumers judge freshness by `availability`. `lastTransmission` is the last write that reached the device, the module's own paints and writes it answered with an HTTP error included, as the device family defines it (review of PR #968, round 2); a change that includes a command's write is published at once, with the command's outcome, and a change from paints alone at most once every 5 s (`TRANSMISSION_MS`), so a painting wall does not republish its record with every paint. A later paint shows with the first device request that settles after the interval, which the 5 s poll bounds while the device answers, and that poll's 1.2 s deadline once it stops; a timer of its own at the interval's end was dropped, since the worker's passes and the poll already rebuild the record at least that often, and no test could tell it apart. The last transmission is a fact of its own (`nanoleaf_transmissions`): the link reports each write that reaches the device, with the request ID of the command whose journal row the worker marked attempting, as the write's span names it, and the module saves it. An outcome, a poll and a restart never change it (review of PR #968, round 2b: deriving it from the last outcome dropped the request ID after any later outcome that sent nothing, and a restart's ended commands overwrote it). A paint that follows a command's write before the record is built still shows at once. A sync is answered with the families it asks for only, since a reader may sync any one of them (Hub #970).
- **Revisions follow the clock.** Each published record's revision is the larger of the last one plus one and the clock's milliseconds, so revisions rise across restarts without a write per publication, and serving a sync writes nothing.
- **`device` is served by owner.** Every device module serves `device` for its own devices (owner-addressed sync, #967), so the Nanoleaf module serves its records beside its own families, health lists them in its `serves`, and a consumer syncs `device` from `bunny/modules/nanoleaf` by name, as the catalog's reader and the module's tests do. The module itself copies only `session`, which the core alone serves.
- **Rendering stays in process.** The renderer is bounded (a few dozen zones and 20 frames each) and synchronous; the module does not move it to `workers.call`. The views are rebuilt on the event loop whenever a request settles, so the saved layout, its geometry and the remembered scene are read again only when their file changes.
- **Device calls are traced.** A device write made for a command records a `bunny.device.call` span in the command's trace, as the playback and LIFX modules do; the module's own paints and reads record none.
- **Favorites are listed in the animation options only.** `nanoleaf-animations` is the options view a play request is chosen from, so it lists the favorites with their names and recipes, which the device record and the wall view never hold. Favorites stay out of browser projections; the wall pages (#934) apply that.
- **The generation guard is defensive inside one runtime.** The feed's generation moves synchronously with each projection, so a stale step cannot arise in one process; a second runtime on the same state is kept out by the workers' lock files, created with mode 600.
- **Waits are whole milliseconds.** The worker waits fractions of a second; the runtime's scheduler refuses a fractional delay, so the module rounds each wait up. Recorded parity keeps the port's own arithmetic.
- **Acknowledgment is a command of the wall.** Python acknowledged from its command line. The module answers `nanoleaf-notice-acknowledge` for a task it shows by sending the core's `notice-acknowledge` for consumer `nanoleaf`, and refuses one it does not show without a request.

## Risks / Trade-offs

- `device/2.0` has no field for a hold, so a hold shows as `degraded` with `held` on the module's own wall view, until #975 adds a `held` member to `device`.
- A mode command's `observed` outcome says the mode committed, not that the wall shows it; the wall's availability says whether it answers, and its paints follow.
- A shipped runtime without a configuration file is `degraded`, with the Nanoleaf module `refused`; the installer (#935) writes the section.
- Codex Desktop's metadata, when configured, is read inside the projection's transaction, as Python read it per poll.
