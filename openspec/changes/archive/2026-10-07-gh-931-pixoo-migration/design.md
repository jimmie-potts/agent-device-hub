## Context

The Pixoo service keeps its library in `<PIXOO_DATA_DIR>/library`: `catalog.sqlite` (WAL, schema version 3 at the installed release `1b4115c`), `owner.sqlite` (a lock file whose exclusive transaction the running service holds) and `media/` (`originals/<content hash>`, and `renditions/<rendition id>/` with a manifest and each frame as raw RGB and as PNG). The Pixoo module (#843) keeps the same library, at schema version 4, in its own SQLite file `modules/pixoo.sqlite` and private folder `modules/pixoo/` under the runtime's state directory, through `Library.attach`. The module's first three migrations are the release's text, so their checksums match the release's `schema_migrations` rows.

## Goals / Non-Goals

**Goals:** carry every asset, rendition, playlist and item with every original and rendition file, byte for byte; never change the source; refuse what cannot be carried safely before writing anything; verify the result with an independent comparison whose zero is the cutover's go; report only counts, codes and hashes.

**Non-Goals:** any other schema version (owner decision, 2026-10-07); a reverse migration; precomputing the module's hosted checks; carrying the player's checkpoint, sessions or pending cleanups (decision 10); orphaned files, which stay in the backup with the rest of the library.

## Decisions

- **The tool lives in `apps/runtime`, the copy in the module.** The module package owns its schema and the library code the copy reuses (`migrate`, `Library.attach`, `verifyStorage`); the runtime owns the state directory's layout, the module's file openers (#919) and the core's lease. The runtime already depends on the module, so the tool can use both; the module cannot depend on the runtime.
- **Read the source immutable, and lock it shared.** A plain read-only open of a WAL catalog leaves `-wal` and `-shm` files behind, which changes the source. An immutable open creates nothing, but ignores a log that holds commits, so a catalog with a non-empty `-wal` or a `-journal` is refused as `source-not-clean`; the service's clean stop folds its log into the file. Immutable reads take no lock, so the tool first takes a shared lock on `owner.sqlite`, whose rollback journal makes a read-only connection write nothing: a running service holds that file exclusively and is refused (`source-in-use`), and a service started during the migration fails to open its library instead of changing it.
- **Check the shape, not only the version.** The source must have the library's application ID, user version 3, the release's three migration checksums, and exactly the tables, indexes and trigger that the library's first three migrations create, compared through `sqlite_master`. A hand-altered table is refused (`source-schema`). The module's own tables have no schema version (#843 hand-off), so the destination must be fresh, and the verifier compares its shape with the library's current schema, ignoring only the module's own `pixoo_*` and the SDK's `bunny_*` tables, as the library's migration does.
- **Write through the library's own code.** The tool creates the installed schema in the destination with the library's first three migrations, inserts the rows in one transaction, copies the files, then calls `Library.attach`, whose forward migration takes the file to version 4, and `verifyStorage`, which reads every copy back against its catalog: each original against its content hash, each frame against its manifest, and each manifest against its row. A file whose bytes do not match fails the migration with `source-corrupt`. The copy itself checks no hash: the library's check after it covers every file, so a second check could never fail alone.
- **Open the destination as the runtime does.** The tool opens the module's database with `openModuleDatabase` and its folder with `openModuleFolder`, so it gets the runtime's modes and checks and #972's WAL with exclusive locking. Only the tool's one connection opens the file while it writes. It closes the database before it reports, which folds the log into the file and removes it, so the verifier's immutable read and the runtime's start find the file whole; the verifier counts a log left with content as a `database` mismatch. Writing through SQLite, rather than copying a database file, meets #972's rule that a copy of a store takes its log or uses SQLite's backup.
- **A fresh destination, removed on failure.** `migrate` refuses a module that has a database, log, journal or a non-empty folder. Once it has begun to write, a failure removes the module's database files and folder, which it proved were absent or empty and which no runtime can open while the tool holds the lease, so a retry needs no manual cleanup. A killed tool leaves an incomplete destination, which `verify` reports as mismatches and `migrate` refuses as not empty.
- **The runtime's own lease.** `holdRuntimeLease` calls the core's `takeLock` with an aborted signal, so it refuses at once while a runtime holds the lease, and holds it until `release`. A runtime that starts meanwhile waits until its core's three-second deadline and fails, as a second runtime does today.
- **Disk space.** `migrate` needs the source files' bytes plus the source catalog's size, an upper bound on the carried rows, plus a margin it leaves free: 256 MiB, or `--min-free-bytes`. A full disk during the copy (`ENOSPC` or `SQLITE_FULL`) is reported as `disk-short` and removes what was written.
- **Independent verifier.** `verify` reopens both libraries: the source as `migrate` does and the destination immutable and read-only. It compares the four tables row by row by ID, checks that the tables that start fresh are empty, hashes every source file and its copy, requires each copy to be a private regular file with one link, and walks the module's folder for anything else. Each kind of mismatch has its own count, so the installer and the operator see what differs without a name or path.
- **Digests for reruns.** Each report carries a SHA-256 over the carried rows and one over the copied files' paths and hashes. Two migrations of one library into fresh destinations give the same report, and `verify` reads back the same digests.
- **No hosted-check precompute.** The module checks each pre-existing hosted multi-frame rendition once after its first start, in the background (#843), so the tool leaves `pixoo_hosted_checks` to it and writes none of the module's own tables.
- **Large GIF canvases.** The release rendered GIFs up to 50 megapixels; the module refuses a canvas over 4,096 x 4,096 when it renders again. The report counts such originals from their stored source, so the owner knows how many can no longer be rendered again, without naming them.

## Fix round 1 (PR #994 reviews)

- **No copy outlives the migration.** The copies share a stop flag: the first failure, or an abort, stops every copy from taking another file, and `migrateLibrary` returns or throws only once every copy under way has finished (`Promise.allSettled`). The tool's removal, its line and the release of its locks therefore never race a copy still writing. Before this, `Promise.all` rejected on the first failure while seven copies wrote on, and the destination was often `left`.
- **The last checkpoint is the tool's.** A close whose checkpoint a full disk stops keeps the log and throws nothing, so the tool reported `migrated` over a store the verifier then found malformed. It now runs `PRAGMA wal_checkpoint(TRUNCATE)` and checks it, closes, and refuses a log or journal left with content (`destination-unclean`). Either fails the migration and removes it.
- **A full disk is `disk-short` at every step.** The library's `migrate` and `Library.attach` wrapped SQLite's error without its cause, so a full disk read as `internal` or `source-corrupt`. `LibraryError` now keeps its cause, and `fullDisk` follows the causes to an `ENOSPC` or `SQLITE_FULL` code, reading no text. The library's `transaction` helper also masked a failed COMMIT, which SQLite has already rolled back, with its failed ROLLBACK; it now rolls back only a transaction still open.
- **Interrupts.** The entry point turns SIGINT and SIGTERM into an abort: before writing, a refusal; while writing, the copies stop, the tool removes what it wrote and exits 4 with one line; while verifying, a refusal. No completion marker is written: the installer gates on `verify` exit 0, and a store killed with SIGKILL fails it.
- **A refusal creates nothing.** The tool opens the source, checks an existing state directory, takes the lease only when its lock file is there (a runtime creates it at its first start and never removes it), checks the module's files and folders and the free space, and only then creates the state directory and the lease file. A module folder or `modules` folder that others may open is refused before the database exists, where it used to fail after it, deleting the operator's folder.
- **Space.** The check counts whole blocks of the file system, the folders and the catalog twice (the database and its log at the last checkpoint).
- **Source.** A library without `owner.sqlite` is `source-not-clean`: without it nothing shows that no service holds the library. A file given as the library is `source-missing`. The report counts the files under `media/` that no catalog entry names.
- **Verifier.** It also requires catalog revision 0 and empty module and SDK tables, so a store the runtime has started on, or changed, does not pass.
- **Known limit, accepted.** The verifier reads the source through the same `InstalledLibrary` as the migration, so a fault in that reader would reach both. The library's own check of the copies, which reads the rows and files through the library's code, and the catalog's NOT NULL columns cover it.

## Boundaries and outcomes

- **Entry points and hand-offs:** the tool's two operations, run by the installer (#935) at the cutover (#840) before the runtime starts; `holdRuntimeLease` for #933's tool. No message crosses the bus: the tool runs while the runtime is stopped.
- **Refusals and outcomes:** a refusal (exit 3) leaves the module's files as they were. `migrate` succeeds (exit 0) or fails after writing began (exit 4, its writes removed unless the line says `"destination": "left"`). There is no uncertain outcome: the tool owns the destination for the whole run, and the verifier is the evidence. `verify` passes (exit 0) or reports mismatches (exit 1). A failed migration is never retried by the tool; the installer decides.
- **Codes:** `usage`, `runtime-running`, `lease-unavailable`, `disk-short`, `destination-not-empty`, `destination-missing`, `module-db-not-private`, `module-folder-not-private`, the state directory's `state-dir-*` codes, `source-missing`, `source-in-use`, `source-not-clean`, `source-schema`, `source-corrupt` and `internal`. Each carries fixed text; none quotes an exception, a path or a name.
- **Diagnostic records:** the tool writes no log records or spans: it runs outside the runtime, and its one JSON line is its record, which the installer keeps with its receipt. That line follows ADR 0011: counts, codes and hashes only.
- **Fault cases:** a running runtime, a running Pixoo service, a short or full disk, a non-empty destination, another schema, an altered table, an unclean log, a missing, linked, oversized or changed file, a manifest that no longer matches its row, and a destination changed after the migration.

## Risks / Trade-offs

- The verifier trusts the source as it reads it at verify time; a source changed between `migrate` and `verify` shows as mismatches, which is the safe direction.
- `source-not-clean` needs the operator to start and stop the Pixoo service once, which folds its log into the catalog, before migrating. The service closes its library on SIGTERM, so a clean stop never needs it.
- A killed `migrate` leaves an incomplete destination behind; `verify` catches it and `migrate` refuses it, and the operator removes the module's two paths before trying again.
