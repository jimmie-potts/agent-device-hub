## Context

ADR 0012's "Observability" rules are settled: each decision is recorded once, by the boundary that makes it, at a fixed level; spans are recorded through `createHostDiagnostics` with no second tracing implementation; replayed work links to its original context; a failing sink never changes a result. #903 made the runtime's records contract records (profile 1.2), and #948 settled what each request result means. The open questions were how the SDK hands decisions and spans to the runtime, which catalog names they use, how spans run without a Collector, and how request IDs that the 1.x attribute refuses are handled.

## Goals / Non-Goals

**Goals:**
- Every command, sync and edge decision makes exactly one record, at the ADR's level, with the work's trace, in process and through the edge.
- Spans with real durations, status and parents or links for each command, each outcome publication and a module's device calls, with no cross-talk between concurrent requests.
- A throwing sink, an exception's message or a replayed outcome never changes a result or reaches a record.
- A polled device that stays offline logs one degradation and one recovery.

**Non-Goals:**
- Export, Grafana and viewing ([#813](https://github.com/jimmie-potts/agent-device-hub/issues/813)), and following one request in a disposable run ([#950](https://github.com/jimmie-potts/agent-device-hub/issues/950)), which reads the runtime's local spans.
- The core's outcome intake and tracker records ([#782](https://github.com/jimmie-potts/agent-device-hub/issues/782), [#831](https://github.com/jimmie-potts/agent-device-hub/issues/831)), and each device module's own domain events.
- Spans for publish, subscribe and sync: the catalog has no names for them, and a message already carries its own span ID.
- A Python local span sink: no Python producer records runtime spans.

## Decisions

- **One typed callback, `onDiagnostic(diagnostic)`.** The bus, the edge and the remote client each take it; the outbox and modules record through the module's `log`. A diagnostic is a closed record: an event, a level and optional scalars that the SDK has already validated (the participant's source, the routing key or `sync <families>`, the request and message IDs, an outcome, a registry code, the edge's route, an error type and an attempt count) plus the trace context. It never holds a payload, an error object or a message. The SDK names events in its own terms (`command.refused`); the runtime maps them to catalog events (`runtime.command.refused`). Rejected: catalog attribute names in the SDK's bus, which would tie the bus to one record format, and a second edge callback beside `log`, which would leave one boundary with two channels.
- **The SDK sets the level.** The boundary knows what it decided, so levels are encoded and tested there: admission, the owner's reply, an expected cancellation and validation refusals at INFO; a refusal for no responder, a full queue or expiry, an uncertain result, an unauthenticated or forbidden edge call and a lost remote stream at WARN; an unexpected edge exception at ERROR; a sync restart after an overflow at DEBUG. Severity never changes a result.
- **Exactly once by construction.** Every bus record about a request is made inside the request's one settlement, or at its admission, so a late reply, a second deadline or a close after settlement makes none. A call the SDK refuses with `SdkError` (a malformed key or deadline) is the caller's error: the bus records nothing for it, and the edge records its refusal of the remote call. A catch that only passes an error to `onError` records nothing.
- **Records under the runtime's scope.** The bus belongs to the runtime, whose bus records already use `runtime.*` (`runtime.delivery.dropped`, `runtime.handler.failed`, `runtime.edge.*`). Profile 1.3 adds `runtime.command.admitted`, `.refused`, `.cancelled`, `.replied` and `.uncertain`, `runtime.sync.served`, `.refused` and `.restarted`, and `runtime.edge.failed`, which carries only `error.type`. Rejected: a new `bunny.sdk` scope, which would split the bus's records from its drop and edge records, and reusing the 1.0 `command.*` events, which describe a controller's own queue.
- **Spans: a small SDK interface, the runtime's implementation.** `SpanRecorder.start(name, {parent, links, kind, attributes})` returns `{context, end(status)}`. The default recorder returns `childOf(parent)` and records nothing, so messages are unchanged without one. Each command gets a `bunny.command.request` span when it is sent in process, or when the edge hands the bus a remote command whose context it authenticated and validated; the command carries that span's context in process, and the bus parents `bunny.command.queue` (admission to dequeue or removal) and `bunny.command.execute` (the handler's run) to it, so concurrent requests never share a parent. The reply carries the execute span's context. A span ends with `error` for an uncertain result or a bus refusal other than cancellation; a typed refusal is not an execution failure. Starting or ending a span never throws into domain work.
- **Outbox publication.** Only the outbox knows whether an outcome goes out for the first time: its row is unpublished until then. Its first publication makes one `outcome.published` record, INFO for `succeeded` and WARN for `failed` or `uncertain`, carrying the outcome's own trace; a replay makes none, so a replayed or duplicate outcome never makes a second record. Each outcome sent gets a `bunny.outcome.publish` span: parented to the stored context when the same transaction stored it, and otherwise, after a restart or a deferred publish, a new root linked to it. A refused publish makes one `outbox.deferred` WARN with the refusal's code and `bunny.outbox.waiting_count`, once per run of refusals as #948's report is, and in its place: given the module's `log`, the deferral is that record and `onError` hears nothing, so one deferral is one record in the runtime; without a `log`, `onError` hears it, and its default stays a `BunnySdkWarning` that names the code and the fixed detail, never the refusal's message. A refusal that `republish()` passes on to its caller is not recorded. The outbox takes these from the module's `log` and `trace`, so they are module records under `bunny.module`, written by the runtime host. Rejected: the host recording publication from `publishMessage`, which cannot tell a replay from a first publication.
- **Device availability.** `DeviceAvailability` takes the module's `log` and clock. A device's first failure logs `device.unavailable` at WARN, later failures are counted and summarized at DEBUG at most once a minute, and the first success after logs `device.available` at INFO with `bunny.attempt_count` and `bunny.duration_ms`. A success while available logs nothing.
- **Request IDs: leave out, do not widen.** `bunny.request.id` keeps profile 1.0's pattern. A record or span whose request ID that pattern refuses keeps everything else and leaves the ID out. Every ID the SDK generates is a UUID, which matches, and the record still carries its trace and message ID. Rejected: a second, 2.0-aligned request attribute, which would make every query check two names for one identity.
- **A bounded local span sink in the host adapter.** `localSpanSink(line, signal)` receives each `projectSpan` document through the span pipeline's existing bounded queue (1,024 records, 4 MiB, drop newest, counted); with a Collector too, it runs first and its failure is counted apart. Tracing needs a Collector or a local span sink. `globalContext: false` installs no process context manager, so spans take explicit parents and several hosts may run in one process; `run` then parents only through its explicit `traceparent`. `schemaVersion` names the profile of the host's records and of its spans' metadata, which is checked as a record of an event its scope allows; the runtime's resource exists only from profile 1.2 on.
- **The runtime's span destination.** The runtime always records spans, at 100% sampling with the parent's sampled flag honored, and passes each finished span to `RuntimeOptions.spans` or, without one, keeps the latest 1,024 in memory for `runtime.spans()`. Span loss (invalid, dropped, unfinished at shutdown, a failed sink) joins `runtime.stopped`'s counts. If the host adapter cannot start, the runtime runs without recorded spans rather than fail. Rejected: spans on stderr, whose lines maintenance intake reads as records, and a span file in the state directory, which #950 can add when it needs one.
- **Profile 1.3, artifact 1.3.0.** Profile 1.2 is #903's, which merged first; a new profile leaves its fixtures, checks and review as they are, as the contract's extension rules ask. The runtime writes 1.3, and every pin moves to 1.3.0 together.
- **Each edge and client decision of #948's fix round has its record.** An exception at the edge is `edge.failed` with the code it answered: `internal`, or `uncertain-result` once it handed a command to its bus. The bus has already recorded that command's own path. The remote client records `remote.command.uncertain` when it settles a request itself: when the edge answers `internal` or `uncertain-result`, cannot be heard by the deadline and grace, or the requester closes first. A refusal it passes on is the edge's record, not the client's.
- **A dropped call is a cancellation.** A stream error while the edge reads a call's body means its caller went away, so the edge records `edge.refused` with `cancelled` at INFO rather than an ERROR `edge.failed`. Only an exception the edge cannot explain is a failure.
- **The verification run watches the adapter.** A disposable run now loads the observability package's host adapter, which the package ships as source, so `apps/runtime/verify/plugin.ts` adds `packages/observability/runtime/**` to `build-current` and its files to the served candidate. This is the only change under `apps/runtime/verify`.

## Risks / Trade-offs

- [Two INFO bus records per command add volume] → They are bounded records within the contract's queues, and admission at INFO is what lets a person follow a request that never got a reply.
- [A span whose parent is a message's own span is not recorded] → A message's span ID is real trace context with no recorded span; the parenting checks accept a recorded span, a message's span or an authenticated remote parent, and fail any other.
- [The remote client no longer reports each failed reconnect to `onError`] → A remote host hears the lost stream and the recovery, with the attempt count, through `onDiagnostic`.
- [`runtime.spans()` keeps spans only in memory] → It is the hand-off to #950; nothing installs the runtime yet.
