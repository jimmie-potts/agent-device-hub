## Context

See proposal.md for why. Today `CodingWorker` (`apps/runtime/src/worker/coding-worker.ts`) keeps one `#running` and refuses a second start with `capacity`. `CodingCoordinator` (`modules/companions/src/coding/coordinator.ts`) keeps one `#active` operation, reports it as `coding-state/2.1` `active`, and answers `endpoint()` with `available` false while a run is active and a revision that moves with every change of the endpoint or its work. The module's `delegate` checks that revision before it sends `coding-dispatch` to the core, whose tracked dispatcher forwards `coding-run` to the coordinator within the thirty-second `coding-run` budget.

## Goals / Non-Goals

**Goals:** three runs at once, one per companion; a tag per run; every run in the published state; a proposal bound to the worker's connection alone; an approved hand-off that waits durably for its own slot and is sent once; per-run settlement; additive contract minors; the page's slot and plan usage view.

**Non-Goals:** a pool of slots shared by companions; a daily cap on coding runs; a second conversation per companion (#2029) or the Apartment room's hand-offs (#2034), which will use the asking companion's slot; queued or steered owner messages (#2030, #2031); any change to the worker's credential role, families, deny list, worktree rules, bounds or results.

## Decisions

1. **A slot is a key, not an object.** The coordinator maps a companion to its slot: the companion itself when the selected endpoint declared at least three slots, else `shared`. A slot is busy while a run holds it, while a dispatch is on its way for it (a reservation keyed by slot), or while the worker's declared total is reached. An older worker that declares nothing counts as one slot shared by every companion, which matches its own `capacity` refusal. Alternative: a slot table with assignments; rejected because the declared count and the companion already decide everything.
2. **The companion comes from the task.** `coding-dispatch` and `coding-run` stay 2.0. The coordinator asks the engine's store for the task's profile when `coding-run` arrives and tags the run; only the worker-facing start (`coding-work/2.1`) and the published state carry it. A start for a worker that declared no slots stays 2.0, which that worker's validator knows.
3. **The binding is the endpoint selection.** `endpoint()` answers `available` while a worker is connected and a revision bound only when an endpoint is selected, disabled or lost. Runs and readiness reports publish new state revisions without moving the binding. `endpoint(companion)` also says whether that companion's slot is busy or has a line, for the page and for diagnosis; the engine proposes either way.
4. **A waiting hand-off is a row, sent by the drain.** `handOff` sends at once only when the slot is free and nothing waits for it; otherwise it inserts `companion_coding_waiting` (operation, task, companion, repository, brief, trace parent) and answers `waiting`, which the engine records as an accepted hand-off whose result arrives later, so the task waits on its delegation question exactly as for a sent one. The drain runs when a run settles, when an endpoint is selected and after a waiting dispatch ends. It takes the oldest row of each free slot, asks the engine whether that task still waits on the delegation and drops the row unsent if not (a cancel the coordinator missed, as during a stop, or one made under an earlier release), then marks it `sending`, reserves the slot and sends `coding-dispatch` with the row's operation ID as request ID. When the core accepts it, or the module already holds its run although the answer was lost, the engine changes the conversation's "Waiting to delegate" line to "Delegated". The coordinator's acceptance of that `coding-run` inserts the responsibility and deletes the row in one savepoint. Any other answer deletes the row and tells the task: refused with the code, or uncertain.
5. **Restart keeps what was never sent and never resends what might have been.** A row still `waiting` at start keeps its place and is sent when an endpoint is selected and its slot is free. A row still `sending` at start had left without its acceptance recorded: it is ended uncertain and delivered as a start-time settlement, so it starts no title check, and it is never sent again. An answer that reaches a stopping coordinator is ignored for the same reason, leaving the row to the next start. The core's tracked dispatcher deduplicates by request ID as a second guard.
6. **Cancel matches where the hand-off is.** A waiting row is deleted and nothing is sent. A row on its way is remembered, and its `coding-run` is refused with `invalid-state` when it arrives, so nothing runs. A run is asked to stop, as before.
7. **The worker keeps stopped runs in their slots until they end.** The core settles every run of a lost endpoint as uncertain. The worker stops those runs, kills a tool that starts after the stop as soon as it appears, keeps each run in its slot, where a cancel or `stop()` still reaches it, and declares the next endpoint once they have ended, or after fifteen seconds (the forced kill at ten, and five more), so a run whose output a leftover process holds open cannot keep every companion without a worker. A run still alive then keeps its own companion's slot busy, so no companion ever has two runs. Stopping the worker waits within the same bound, so a stopped run's git steps finish before the process lets go. A stopped run's later report is dropped rather than sent on the new endpoint. Fix round 1 on PR 2087 replaced an earlier design that cleared the slots at once and could leave a late-starting tool unreachable. Each repository's fetch and worktree add run one at a time, so runs on the same repository never race git's locks; each still gets its own fresh worktree.
8. **The page reads only the published state.** Slot lines, the waiting card and the approval note are pure functions of `coding-state/2.2` (`src/frontend/coding-status.ts`). Plan usage lists the windows the worker's readiness reported after its latest run, with when they were observed; they are shared by every run.

## Risks / Trade-offs

- [A run the core gave up on while the worker still runs it (its start report lost) holds that companion's worker slot] → the next hand-off for that companion is refused by the worker with `capacity` and its task is told so; nothing is retried. This needs a lost start report and is bounded by the run's own wall clock.
- [The worker reports a run started before its git setup, which takes turns per repository] → the coordinator's deadline after a start adds one setup bound per slot (240 seconds each) to the wall clock and grace, so a queued setup never spends a later run's grace; a connected but silent worker's run is given up as uncertain about 34 minutes after its start report instead of 22. A lost worker's runs still end at once.
- [A waiting hand-off has no deadline of its own] → each run ahead of it is bounded by its wall clock and grace, and the owner can cancel it; at most 32 hand-offs wait.
- [An approval for a busy slot runs later than the owner approved it] → the approval text and the waiting card say so, and Cancel removes it unsent; the owner chose this (held approval).
- [A new worker cannot declare to an older core] → the core is upgraded first, as for every coding contract since #1743.
