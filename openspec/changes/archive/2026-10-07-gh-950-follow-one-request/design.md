## Context

ADR 0012's "Observability" settles that spans are recorded through the host adapter's bounded local span sink, that a disposable run samples every request so one request can be followed unless a queue bound drops its records, and that a missing record is reported as missing. #949 recorded the spans and kept the latest 1,024 in the runtime's memory, and rejected a span file then, leaving it for this story. The run's supervisor already holds the runtime's journal records, which it reads from the child's stderr as the service manager's journal would, with the generation of the runtime that wrote each. The open questions were where a run's spans go so that they survive a crash and are readable from outside the process, how the query keeps secrets and payloads out, how it tells a lost span from one that never existed, and where an operator asks it.

## Goals / Non-Goals

**Goals:**
- One request or trace, in a disposable run, shows its bounded, redacted records and spans as JSON, in each of four cases (success, refusal, uncertain effect, replayed outcome), with capped and missing evidence reported as such.
- Every way the evidence is incomplete is named, and absence is never reported as proof.
- No secret, payload, message or raw error reaches the answer, however a record or span arrived.
- The installed runtime and the run's boundaries (no installed service, personal state or device) are unchanged.

**Non-Goals:**
- Export, a viewer, Grafana and Explore ([#813](https://github.com/jimmie-potts/agent-device-hub/issues/813)).
- New records, span names or a contract profile; the catalog stays 1.3.
- A new operation in the core or in the host route: the core's operations are shared with other adapters, and the host route runs only them.
- Following a request across runs, or through the installed runtime.

## Decisions

- **A file pair in the state directory, written by the runtime through the existing `localSpanSink`.** The span must outlive a kill and be readable by another process; the supervisor already runs outside the runtime, and the state directory is validated private, outside every checkout and off Windows mounts. The runtime's `spans` option takes `'state-file'` beside a sink, so the same adapter queue, counts and shutdown flush apply and no second tracing path exists. Rejected: spans over the child's IPC channel, which would lose what a kill leaves queued in the child and would not work for the shipped entry point that device stories will use, and a flag on every runtime for a file path, which would have to be validated again.
- **A ring of two segments, latest wins.** `runtime.spans()` keeps the latest 1,024 and counts the evicted; a file that dropped the newest instead would make a long exploring run unable to follow its newest request. Two segments of 512 spans or 2 MiB, the next replacing the one before it, hold the latest spans, up to 1,024 (at least 512 unless spans are large, since each segment also rotates at 2 MiB), within the contract's 1,024 records and 4 MiB. Each segment's header line counts the spans let go, so a reader tells an evicted span from one that never arrived, and a restarted runtime continues the files and the count. A kill between the rename and the new header leaves a current segment that is missing or empty beside a previous one: the next runtime's header says the count is unknown, never 0, and the reader reports it as unknown. Rejected: one file rewritten on every span, which does I/O proportional to the bound on the hot path, and a count held only in the runtime's memory, which a kill loses.
- **Writes are synchronous and small.** A span line is at most 8 KiB and goes to the page cache before the sink returns, so a span finished before a kill is in the file. The sink throws when it cannot write, so the host adapter counts the span as lost and `runtime.stopped` reports it. The file never changes a result.
- **Private by construction.** Both files open with `O_NOFOLLOW` at mode 600 and must be regular files of the runtime's user with one link, as the module databases are; anything else refuses the start with `span-file-not-private`, before a module starts. The reader opens without following links and reads each segment to its byte bound and a little more, whatever the file's size.
- **Validate, then project.** The query never copies a field from a raw line. A journal record must pass `validateRecord`, and a span must be shaped as the adapter projects it and pass the same record checks the adapter made when it started the span (its resource, scope and attributes as a record of an event its scope allows). What fails is counted and shown nowhere. The answer is built from the validated values: the registered attributes, ids, times and fixed enumerations. A secret cannot arrive in an attribute the catalog bounds, and it cannot arrive in a field the answer never copies. Rejected: filtering known-bad strings, which proves nothing about the next one.
- **A request ID takes only what carries it.** Records and spans match on `bunny.request.id`, never on the trace, so two requests that share a trace never leak into each other's answer, as a caller-supplied parent would make them. The answer counts what else the traces hold (`otherOnTrace`) and a query by trace reads it. A trace query also takes the spans of other traces that link to it, which is how a replay, a new root linked to the stored context, is found from the original command. Rejected: matching the request's whole trace, which would show another request's records as its own.
- **Absence has names.** `none-found` carries a fixed note, and the gaps list every way the evidence is incomplete: a runtime that ended without `runtime.stopped` (a kill or crash; a clean stop writes it), telemetry the runtime reported lost at its stop, evicted spans, an unknown eviction count, a read at its bound, no readable span file, records and spans the contract refused, spans whose parent is missing, and the query's own caps. A span that never ended is not reported, and the answer counts spans by name so a name with no span is absent, not zero. A killed runtime's request span never ends, so its finished children name a parent that is not kept; that is the evidence of loss. A remote command's server span continues the caller's context, which the run does not record, so its parent is `caller`, not missing; the same holds for a module's device call that continues it, and for a publish span that continues a stored message's context.
- **An ending belongs to the command it follows.** The bus records a refusal for no responder or a full queue with no admission, so counting endings against admissions would call an admitted command ended because another command was refused. The answer pairs each ending with the admission of the same message ID and reports how many admitted commands have none (`unended`); a refusal that was never admitted ends no admitted command. Rejected: pairing by order, which a restart's interleaved generations break.
- **Every cap is counted.** The records, spans, endings and trace IDs an answer leaves out are counted in `omitted` and make the `capped` gap, and `endings` follows the record limit as the records do, with the verdict (`admitted`, `unended`, `ended`) still covering every matched command. A silent cap would let an answer look complete.
- **A live runtime is a standing gap.** A runtime counts what its queues dropped and its sinks lost only in `runtime.stopped`, and loses it if it ends abruptly. An answer about a runtime that has not recorded its stop, whether it is live or was killed and not yet restarted, therefore names it (`losses-uncounted`), found or not, and a `none-found` note carries the same caveats as a `found` one. Rejected: reporting the gap only for a run that crashed, which hides the losses of the run that did not.
- **Each parameter once.** A repeated `request`, `trace`, `records` or `spans` is refused with the same fixed 400, since an answer for one of two requests is an answer for neither; a parameter the query does not know is ignored.
- **The journal counts what it does not take.** The supervisor keeps each stderr line that is a JSON object with an event name and counts every other line with content, so a stack trace or a usage line is part of the `unreadable` gap instead of vanishing.
- **A failed segment start is retried.** A rotation that cannot rename or create the next segment loses that span and counts it; the next span starts the segment, with the count the rotation had worked out, so recording recovers once the cause has gone. A restart that finds no current segment, or an empty one, beside a previous one writes an unknown count, never 0.
- **The supervisor answers; the capture step proves.** The supervisor holds the journal, the generations and the state directory, and its harness API is already loopback-only with the run's host checks, so the query is one more read route there. The capture step is how a reviewer reaches it through the core's operations, including the host route, which runs only those. A new core operation would change every adapter and the host route's allow-list for one app. The step runs the cases, attaches each answer and judges it.
- **The journal drains before the next runtime starts.** The child's exit can come before its last stderr lines are read, so a clean stop's `runtime.stopped` could be missing and the query would call a clean runtime killed. The supervisor waits for the child's stdio to close, for at most a second, which a descendant that kept the pipe open costs and no more. It also passes `--log-level info` so that the level the query reports is the level the run asked for.
- **Boundaries and outcomes.** The query is read-only, loopback and local-only, and starts nothing. A malformed selector is `invalid-request` (400, not retryable) with a fixed message. A request the run cannot find is `none-found`, a successful answer with its gaps. The runs never touch installed services, personal state or devices; the span file is in the run's own state directory, which `stop` removes with the runtime directory. Trace continuity is unchanged: records and spans carry the traces #949 gave them.

## Risks / Trade-offs

- [The file holds the latest spans, up to 1,024 and fewer when they are large, so a long exploring run loses its oldest] → The header counts what was let go and the answer names it, as `runtime.spans()` does for memory; a `fresh` capture step and a reseed start a new file.
- [A synchronous write on the runtime's event loop] → One small write to the page cache per finished span, behind a flag that only a disposable run passes; the installed runtime is unchanged.
- [The query validates every record on each call] → A run's journal is small and a run is short-lived; the answer is bounded to 100 records and 100 spans whatever the run holds.
- [The supervisor keeps every journal record in memory, as it did before] → Unchanged here; a run is bounded by its lease.
- [A parent's `caller` state trusts the server request span] → Only a retained `bunny.command.request` server span marks its parent's context as the caller's, and a span with no such span is `missing`, which is the conservative answer.
