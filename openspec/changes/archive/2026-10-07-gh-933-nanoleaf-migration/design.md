## Context

The codex-nanoleaf bridge keeps its state in a private Linux state directory: `status.sqlite` (rollback journal mode, model version 4 with each row's device since the in-place migration of ADR 0009), `config.json` (the device registry, with each token under the key its `token_ref` names, the bridge's ports and Codex Desktop's metadata paths), `layout.json` (a version 2 layout per device, or the older Lines-only `line_groups`), `scene-state.json` and `scene-state.<device>.json`, and lock files: each device's worker holds `notification-lock*.sqlite` exclusively while it runs, enrollment holds `registry-lock.sqlite` and layout discovery `layout-lock.sqlite`. The installed bridge's schema-defining files are byte-identical to codex-nanoleaf `c711e18`, the commit the port came from (the coordinator compared code files only). The Nanoleaf module (#844) keeps the same tables, created by the port's `initialize` and its own `MODULE_TABLES`, in `modules/nanoleaf.sqlite`, and its layout and scene files in `modules/nanoleaf/`. Its configuration section (#919) names each device's address and the secret file of its token, and its qualified sources.

## Goals / Non-Goals

**Goals:** carry the owner's per-store "migrate" rows for Nanoleaf: the layout, preferences, project map and colors, palette, scenes and favorites, and the addresses and tokens; never change the source; refuse what cannot be carried safely before writing anything; verify the result with an independent comparison whose zero is the cutover's go; report only counts, codes and hashes; keep every token out of everything but its secret file.

**Non-Goals:** the enrollment command (owner decision, 2026-10-07: it waits until needed); tasks, reservations, epochs, display caches and the controller ledger (decision 10); legacy rows and `bindings` (#26); renaming a device ID that is not a routing ID; any other schema; a reverse migration.

## Decisions

- **The tool lives in `apps/runtime`, the copy in the module.** The module owns its schema, the port's readers (`registry`, `layoutDevices`, the scene check) and its `configure`; the runtime owns the state directory's layout, the module's file openers, the core's lease and the secret reader. The runtime depends on the module, so the tool uses both, as #931's Pixoo migration does.
- **What "preferences" covers.** Besides each element's project and halves and the map settings, each device's mode (Work, Quiet or Free) and its native power and brightness overrides carry over: codex-nanoleaf protects "the user's mode and scene selection", the module publishes them as the device's desired state, and none follows live sessions. The mode's revision and applied counters carry with it, so a mode the bridge's worker had not yet applied is applied by the module's. A pending wall edit carries too: the module keeps one across its own restarts and applies it once no comet runs, which after the cutover is its first pass. Every other `meta` value (epochs, the display's dirty flag and receipt, holds, failures) starts fresh and is counted.
- **Read the source under its own locks.** `status.sqlite` opens read-only through a URI, so SQLite's read-only mode applies: in rollback journal mode it writes nothing, and a journal left by a killed writer is refused (`source-not-clean`) instead of rolled back. A WAL database is refused as another schema, since a read-only open could create `-wal` and `-shm` files beside it and the bridge never used WAL. The tool holds a read transaction on it for the whole run, and shared locks on the bridge's registry, layout and worker lock files, so a running worker or enrollment is refused (`source-in-use`), a worker that a hook launches meanwhile fails to take its lock, and no bridge process commits while the tool reads. Every JSON file opens without following a link, bounded in size.
- **Copy by SQL, with storage classes.** The destination's tables come from the module's own schema code (`initialize`, then `MODULE_TABLES`), as its start creates them. The source is attached to the destination's connection read-only and immutable, which the held read lock keeps stable, and each carried table is copied by `INSERT ... SELECT` in one transaction, so `5`, `5.0` and `'5'` stay distinct. A pre-change table without `device` gives every row to the Lines, as the bridge's own migration does. Only the registered devices' rows and `meta` keys are copied.
- **Check the shape of what is read.** The source must be model version 4, and each carried table must have exactly its columns (or lack only `device`, on all of them or none); a carried table with another column would lose it and is refused (`source-schema`). Tables the migration leaves behind are only counted.
- **Files as the port writes them.** The layout of the registered devices is the port's `serialized` version 2 layout, so a Lines-only layout gains its elements; scene files keep their parsed content, checked with the restorer's own rule (`validSceneState`). Each is a new file, mode 600, synced, with the folder synced after.
- **Tokens become secret files.** Each device's token goes, alone and without a line break, to `nanoleaf-<device>-token` in the secrets directory, mode 600, created exclusively; the section names it as `<device>-token`. A token must be printable ASCII without spaces, so the runtime's reader, which strips trailing line breaks, gives it back unchanged. The section is checked by the module's own `configure` before anything is written, and written as a private file for the installer, which puts it under `modules.nanoleaf`. Its addresses and paths are personal data, so the section's directory must be private too.
- **Open the destination as the runtime does.** The tool opens the module's database with `openModuleDatabase`, which checks the file and opens it through the SDK's `openModuleDatabaseFile` (#972): exclusive locking, so no `-shm` file, and WAL at `synchronous = FULL`. Its folder comes from `openModuleFolder`. The tool closes the database before it reports, which checkpoints the log into the file and removes it, so the verifier finds the file whole and counts a `-wal` or `-journal` file with content as a mismatch.
- **Never drop a lock it holds.** A lock is a POSIX lock, which closing any descriptor of its file drops. The bridge's lock files and `status.sqlite` open only through SQLite, except for one plain read of the database's header before any lock on it is taken, and one process opens a source once at a time (`source-in-use` for a second reader), so that read never closes a descriptor of a locked file. The destination is likewise only `lstat`ed while it is open.
- **A fresh destination, removed on failure.** `migrate` refuses a module that has a database, log, journal or a non-empty folder, and an existing secret file or section. Once it has begun to write, a failure removes the module's database files and folder and each file it created; a file whose exclusive create failed was someone else's and is left. A killed tool leaves an incomplete destination, which `verify` reports as mismatches and `migrate` refuses as not empty.
- **The runtime's own lease.** `holdRuntimeLease` is #931's helper over the core's `takeLock`, byte-identical here; it refuses at once while a runtime holds the lease, and a runtime that starts meanwhile fails at its core's three-second deadline.
- **Independent verifier.** `verify` reopens the source as `migrate` does and the destination immutable and read-only. It compares each carried table by its key, values with their storage classes, checks the destination's schema against the module's own and that everything else starts fresh, compares each file as parsed JSON and its modes, walks the folder for anything else, compares the section member by member, each device on its own, and reads each secret through the runtime's `loadSecret`, comparing digests in constant time. It reads `--section` as the section file or as the configuration file that holds it, so the installer can verify the file the runtime will read.
- **Digests for reruns.** Each report carries a SHA-256 over the carried rows, one over the written files and one over the section's canonical JSON, which holds paths and no token. Two migrations of one source give the same report, and `verify` reads back the same digests.
- **No enrollment command.** An address change is a one-line edit of the device's `address` in the section; the device's ID, and with it every carried row, stays. Adding a device waits for the command; `src/enrollment.ts` is ready for it.

## Boundaries and outcomes

- **Entry points and hand-offs:** the tool's two operations, run by the installer (#935) at the cutover (#840) before the runtime's first start, with the section it writes going under `modules.nanoleaf` (#935) and `verify` as the go (#840). No message crosses the bus: the tool runs while the runtime is stopped and holds its lease.
- **Refusals and outcomes:** a refusal (exit 3) writes nothing. `migrate` succeeds (exit 0) or fails after writing began (exit 4, its writes removed unless the line says `"destination": "left"`). There is no uncertain outcome: the tool owns the destination for the whole run, and the verifier is the evidence. `verify` passes (exit 0) or reports mismatches (exit 1). Nothing retries; the installer decides.
- **Codes:** `usage`, `runtime-running`, `lease-unavailable`, `secrets-dir-refused`, `section-dir-refused`, `destination-not-empty`, `destination-missing`, `module-db-not-private`, `module-folder-not-private`, the state directory's `state-dir-*` codes, `source-missing`, `source-in-use`, `source-not-clean`, `source-schema`, `source-corrupt`, `source-config`, `source-device-id`, `source-not-configured`, `disk-short` and `internal`. Each carries fixed text; none quotes an exception, a path, an address, a token or a name.
- **Diagnostic records:** the tool writes no log records or spans: it runs outside the runtime, and its one JSON line is its record, which the installer keeps with its receipt. That line follows ADR 0011 and ADR 0012's safe errors: counts, codes and hashes only.
- **Fault cases:** a running runtime, a running bridge worker or enrollment, a writer killed mid-transaction, another schema or an added column, WAL mode, damaged or linked files, a malformed registry, a device ID that is not a routing ID, a public address, a missing or unreadable token, an unconfigured shared input, a non-private secrets or section directory, a non-empty destination, a file made by another process during the write, a full disk, and a destination changed after the migration.

## Risks / Trade-offs

- The verifier trusts the source as it reads it at verify time; a source changed between `migrate` and `verify` shows as mismatches, which is the safe direction.
- Carrying the mode and the native overrides means a wall the owner switched off natively stays off after the cutover, and a Free wall stays Free, until an explicit mode command, as on the bridge. The cutover's mode checks (#840) set each mode anyway.
- A registered device ID that is not a routing ID is refused rather than renamed; the installed devices are `wall` and the NL22's enrollment default `panels`. Renaming would rewrite every carried key and file name, and waits until a real ID needs it.
- `source-not-clean` needs the operator to start and stop the bridge once, which rolls its journal back, before migrating.
- A killed `migrate` leaves an incomplete destination behind; `verify` catches it and `migrate` refuses it, and the operator removes the module's two paths, the secret files and the section before trying again.
