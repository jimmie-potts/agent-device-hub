The issue stays aligned. The adjustments below are routine and within its accepted scope.

## Goals / Non-Goals

**Goals:**
- The controller's queue, protocol, lease and status behavior in a runtime module, with their tests, under the strict profile and the module boundary.
- Every command answered: refused before any effect, or stored, accepted and completed with one outcome through the outbox, never sent again.
- Policy A: start never waits on a bulb, and an unreachable bulb is an `unavailable` record with one degradation and one recovery.
- Tier 1 and tier 2 scenarios with simulated bulbs.

**Non-Goals:**
- The Beam's qualification (#319, #320, #327), outside-change detection (#362) and the Hub mode (#415), the issue's cuts.
- The core's acknowledgment of outcomes (#782), pages, tools and settings (#835), the installer that runs the conversion (#935), installation and the physical check (#840).

## Decisions

- **Copy, then convert.** The queue keeps one job at a time, a bounded queue, the LightGet before each read-modify-write, bounded attempts with the same absolute payload, a write without an acknowledgment as possibly applied, and a closed queue that sends nothing more. The controller v1 envelope goes: the module answers 2.0 commands itself, so admission, `nextRequestId`, epochs, receipt caches and the lighting profile schema have no place. Their protections move to the module's refusals (`revision-conflict`, `duplicate-conflict`, `capacity`, `unsupported-capability`) and to the store. The old package stays, so the installed service keeps building until #839.
- **Each attempt's deadline on the module's scheduler.** The old queue used `setTimeout`. The module's scheduler follows the runtime's clock, so the catalog's manual clock drives it, and the runtime cancels it at stop. The copied tests lose their busy-wait stalls and mocked timers and keep their assertions.
- **Stop aborts the call in flight.** The old host's `closeGracefully` let an in-flight paint finish. A module's timers are cancelled when it stops and the SDK aborts its `signal`, so the module closes each queue: what waits sends nothing, and the call in flight is aborted. Cancellation is not undo (ADR 0012), so that command's outcome is `uncertain`. Alternative rejected: real timers during stop, which would outlast the runtime's view of the module.
- **The store before the reply, never the command.** An accepted command is a row with its source, `requestId`, a digest of its body, its family, its bulb, its state (`accepted`, `started`, `done`) and its trace context, written in the outbox's transaction with the record that shows it pending. A store that refuses refuses the command (`capacity` for SQLite's full-disk code, otherwise `internal`). The row turns `started` before any packet, so a restart can tell `uncertain` from `failed`; the mode change and its outcome commit together, so a mode row never needs `started`. Completed rows answer repeats; the newest 1024 are kept.
- **Outcomes by MAPPING.md's receipt rule.** An acknowledged write is `succeeded` with `transmitted`. A committed mode change is too, as the old controller's `mode.set` receipt (`sent`, `confirmed-transmission`) maps; it never reaches the transport, so it sets no `lastTransmission`. A write without an acknowledgment is `uncertain` with `none`. A failure before a write is `failed` with `unavailable`, and work the stop retired is `failed` with `cancelled`.
- **Retries within the command.** ADR 0012 lets a module repeat an idempotent write its protocol expects to be repeated, inside the command's deadline and a counted budget. The queue keeps `retries` (default 1) and starts no retry after the command's `expiresat`; tests count the packets.
- **Device families and a module family.** General controls use the #918 families on the device's own keys, since responders may not overlap. Color and kelvin are the module's `lifx-color-set` and `lifx-temperature-set`, with the general commands' guards, and `lifx-light` carries the color capabilities and reading, in degrees and percent, beside the device record. The edge registers the device families once, in the runtime, rather than each device module adding them to its schemas, which would lose their checks.
- **Status from the copy.** The module syncs `session` from the core and keeps a map of the changes until its first sync resolves, then reads the copy itself, so a resync is never seen half applied. The shown key is kept in the module's database: the issue's "a restart sends nothing" and "only when the shown status changes" both hold, a manual change survives a restart, and a status that changed while the module was stopped paints once. The old publisher painted once at every start; the persisted key is the deliberate difference.
- **The status block stays opt-in.** A qualified bulb paints only with status caps in its section, as the old host painted only with a bulb's `status` block and the host's feed. The conversion keeps the caps only when both were present.
- **One LightGet at start.** Policy A needs the module to learn a bulb's availability without a command, and the kit's offline check expects an `unavailable` record. A LightGet changes nothing on the bulb, so a restart still writes nothing. An unreachable bulb is read again after 30 s, doubling to 5 minutes, which `DeviceAvailability` logs as one degradation and one recovery. Alternative rejected: no polling at all, which would leave a recovered bulb `unavailable` until someone commanded it.
- **The on-demand read follows sync.** The old host read a stale bulb when its snapshot was read over HTTP. In 2.0 a consumer reads by syncing, so a sync of the module's records starts one LightGet per stale, reachable, qualified bulb, at most one per bulb every 30 s.
- **Leases in the private folder.** The writer lease is the Tidbyt runner's exclusive SQLite transaction, one file per address in `files()/leases/`. A held lease makes that bulb `unavailable` and refuses its commands; the module runs on.
- **The conversion in the module.** The installer imports `convertLegacyConfiguration` and `readLegacyModes`, so the rules that read the old files stay with the code that knows the section, and the result passes the module's own `configure`. The old mode files are read with the old controller's fail-closed rules.
- **Acknowledgments by option.** Until #782 defines the core's acknowledgment, the module takes an `acknowledgments` follower; tests, the in-memory harness and disposable runs pass the kit's stand-in, and the shipped module keeps its outcomes and sends them again at each start, as the SDK README says.
- **Simulated bulbs at the packet level.** `SimulatedLifx` implements the transport the real `UdpTransport` does, so the queue, retries and deadlines run unchanged. In a disposable run the supervisor holds it, and the runtime child forwards each packet over IPC, as it does for the fixture sign.
- **The shipped list.** The module's factory has the runtime's `ModuleFactory` shape without importing the runtime. A shipped runtime without a configuration file refuses the module with `not-found`; the process tests now expect each shipped device module refused, so the next module story's entry needs no test edit.

### Review fixes (PR #965)

- **Simulated sections on the factory.** The shipped list's device modules declare `configure`, so a run without a configuration refuses them at ERROR, which maintenance intake takes as a finding. The factory gives a `simulatedSection`, the field #844's PR #968 adds to `ModuleFactory`, in the shape its review settled: `{config, secrets?}`, the section without its `secrets` member and the secret names it needs. One helper, `simulatedSections`, builds each module's section with one synthetic token file per name, for the maintenance test's clean run, the runtime's tests and the `shipped` disposable run, so every device PR uses one mechanism instead of a per-test table. The LIFX module reads no secret and names none.
- **Reads publish only changes.** A read used to republish both records, because a new observation time made them differ. A read now publishes the device record only when availability, power or brightness changed, and the color record only when hue, saturation, brightness or kelvin changed (ADR 0012, "Repetition"). Each record keeps the reading it was last published with, so a sync serves the same content at the same revision; the cost is an `observedAtMs` that names the last reading that changed something, not the latest one.
- **The deadline before every packet.** A job's turn can come after its command's deadline, and a LightGet can outlast it. The queue now checks the deadline at the job's turn, before every attempt, the first included, and just before the write. Such a command ends `failed` with `expired` and sends nothing; a mode change past its deadline changes nothing. `expired` is the registry's code for "arrived after its expiry", and here the work arrived at the bulb after it.
- **Started at the write.** The work is marked begun inside the job, just before its write, so after a crash a command that waited in the queue or only read the bulb is `failed` with `cancelled`, and only one whose write may have gone out is `uncertain`. A store that cannot make the mark fails the command with no effect; the trade-off is one more store write in the job's turn.
- **Settle all but a busy bulb's commands.** At start the module reports the unfinished commands of bulbs whose lease it holds, of a bulb no longer configured, and of a bulb whose lease it could not take for another reason than another holder, since ADR 0012 has the owner report an outcome for each accepted command that has none. It skips only a bulb whose lease another holder has (`busy`): another instance on the same state directory, which the core's own lease already rules out in the runtime, may still have that work in hand (fix round 2).
- **One reading of the clock before a write.** The check just before the write also decides the write's first attempt. A second reading after the work was marked begun could find the deadline passed and report a write that never went out as possibly applied, and the bulb as unavailable (fix round 2).
- **`command.executing` at the turn.** The record and the device call span start when the command's turn comes within its deadline, not when it is accepted, so a command that expired waiting shows no device work (fix round 2).
- **Lease refusals say why.** `busy` for another holder, `not-private` for a folder or file that is not private or is a link, and `failed` for one that could not be opened, each with its record reason (`busy`, `unauthorized`, `unavailable`) and its command refusal. A second take in the same process is refused before it opens the file, because closing a second descriptor drops every POSIX lock the process holds on that file.
- **A call ends when its transport says so.** An attempt's deadline and the queue's close abort the transport's call and wait for it to settle, rather than give up on it at once, so a stop waits for the call in flight before it stores the outcome and releases the lease. The transport contract says an exchange settles once its signal aborts; the stop deadline bounds one that does not.
- **The on-demand read covers an unavailable bulb.** As the old host did, a sync of the records reads any stale qualified bulb, at most once per bulb every 30 s, counting the probe's reads, so a bulb that came back shows `available` within 30 s of a reader's sync. The read follows each sync request, not a follower that stays subscribed.

## Risks / Trade-offs

- [The shipped runtime is `degraded` without a configuration file] → The installed runtime always has one (#935); health names the refusal.
- [Outcomes grow until #782] → The SDK's documented limit; each start resends them, and the fixture core acknowledges them.
- [A paint over a session record that a resync replaced] → The module reads the whole copy once it has one.
- [A start reads each bulb] → One read-only LightGet per qualified bulb; documented as the only traffic a restart sends.
