## Context

The Pixoo module's presentation (`modules/pixoo/src/presentation/monitor-presentation.ts`) is organised around two native modes that are at once policy and content switch. The Hub-mode owner (`apps/runtime/src/core/mode.ts`) fans out `device-mode-set` through `HUB_MODE_TABLE`, which maps the Pixoo lossily. ADR 0014 records the owner's decisions; this design covers how the module and core carry them without a new state owner, writer or contract family. A design is required because the change replaces persistent presentation state, changes an admitted record's shape and touches a device-command boundary.

## Goals / Non-Goals

Goals: one mode vocabulary, mode as policy, two bases, the Work set, Quiet brightness with the remembered value, per-base moment admission, and a migration that needs no installed configuration edit. Non-goals: Hub-wide Quiet semantics, per-playlist Work flags, a configurable Work set, the Tidbyt and LIFX behavior, the legacy 1.x surfaces, and any physical claim from source tests.

## Decisions

- **Mode is a flag the presentation reads, as the Nanoleaf's `_mode` is.** `device-mode-set` saves the mode in the module's state table (new key, Free when absent), publishes the record, then applies policy: in Work, stop the player if it holds an active or paused item; in Quiet, write the Quiet brightness; on leaving Quiet, write the remembered brightness. No other effect. The saved mode is read at startup for the record only; startup writes nothing, matching the Hub's no-replay rule. Alternative rejected: keeping a separate presentation mode derived from the Hub mode, which reintroduces the mapping.
- **One base derived from the player, not a stored selection.** `base` is `playback` while the player holds an item (active or paused) and `status` otherwise. Stop, Clear and a finished playlist return to status through the existing blank-then-dashboard path. Alternative rejected: an explicit three-way selection with "nothing", which keeps the blank-Media state and needs a command to leave it.
- **Work refusal at admission, not at the player.** `media-start`, `pixoo-media-show`, `resume` and `restart-with-changes` are refused `invalid-state` with detail "not admitted in Work" in the admission queue, where `requireMode` was checked, so the check and a concurrent mode change cannot race. `pause`, `stop`, `clear`, `next` and `previous` stay admitted in Work (they only reduce or keep what plays; on a stopped player `next` and `previous` are refused as before). A `media-start` accepted in Free and still capturing when Work arrives is cancelled through the player's generation, as a manual stop cancels it today.
- **Remembered brightness is the last requested value before Quiet.** It is saved in the state table when Quiet is entered from Work or Free and cleared when Quiet is left. A `brightness-set` during Quiet updates the player's requested brightness only; the next mode command reapplies policy, so a Quiet command received while already in Quiet (an individual override or a Hub reapply resolving to Quiet) rewrites the Quiet level, while a Work or Free command received in that same mode writes nothing. The Quiet level is `quietBrightness` in the `pixoo` section, integer 1 to 100, default 20; the lower bound keeps a mode change from blanking the panel.
- **Per-base admission replaces per-mode admission.** `momentBlock` keeps its shared gates (closed, pending mode, screen off, offline, pending start, attention, Now Playing takeover, another moment). Over status it requires the session source to be current, the "moments over status" setting on, and `coversStatus` only when the mode is Work. Over playback it admits an active item (pause and resume in place) and refuses a paused one. The stopped-media and empty-pause branches are removed with their persisted `emptyIntent` key, which a later start ignores.
- **`pixoo-display/2.1`.** `mode: work|free|quiet`, `pendingMode` the same, `base: status|playback`, `participating` kept (status base drawn and current), `moments.overStatus` replacing `overMonitor`; `showing`, `monitor`, `nowPlaying` and `player` unchanged. A closed enum change is not additive, so this is a new minor that the module publishes alone. The runtime dashboard is the only reader, so #1574's own PR carries the minimal reader adaptation (sync and read 2.1, gate content controls by the advertised Hub mode, drop the `native()` reverse map) and main never holds a module and a dashboard that disagree on the record; the dashboard's visible redesign (labels, routine editor, display card, the Moments switch) stays with #1575, and the install is gated by #1576. `pixoo-moments-set` keeps its name and takes `overStatus`.
- **Shared contracts.** `HUB_MODE_TABLE.pixoo` becomes the identity, `nativeMode` is kept for the Nanoleaf and LIFX callers, the schema text for `nativeMode` names the Nanoleaf example, and the `device-mode-set`, `media-start` and `media-control` schemas keep their shape. `requireMode` stays in the shared 2.0 schemas because removing a member from a closed minor is not additive; the Pixoo refuses it and the core stops sending it, and the message-profile "General device commands" requirement says so. `pixoo-media-show/2.0` drops its `requireMode` member, which only the core set.
- **The status base draws itself, and a failure holds it.** The status base is not a mode: whenever the player holds no item and no start is capturing one, the presentation draws it under the player's current generation, with no pause. A device's start therefore draws it at once, as the old Monitor restore did, and a simulator's start stays passive until a mode or player command, as divoom-app-upgrade#77 kept it. A failed or uncertain status write, including a moment's over the status base, holds the status base until a mode or player command, as a failed dashboard stopped Monitor until it was chosen again; this keeps an uncertain write from being repainted on every tick. A view change redraws a status base already drawn and does not end a hold.
- **Routines.** The content-mode fields (`DEFAULT_CONTENT_MODE`, the kind-derived content mode) become an optional `runsOnlyIn: work|free|quiet` on any action, checked by the core against the target device's reported desired mode immediately before the send and logged `blocked` with reason `mode` as today. Stored routines that carry a `device-mode-set` with `monitor` or `media` are refused at send time by the Pixoo's `commandSupported` check as an unadvertised mode; the Mac holds none, and the editor stops offering them. A stored action may still carry the retired `requireMode` (every stored Pixoo content action carries `media`, since the core filled it in), and a stored row the reader refuses fails the core's open, so a stored row reads it as `runsOnlyIn` for the Hub mode it stood for: `media` as `free`, `monitor` as `work` (Monitor's first meaning), and the Hub's own values unchanged. A new definition cannot use it. Content families stay limited to the kinds that show content (Pixoo and Nanoleaf), which the removed content-mode table used to enforce. Log rows record `runsOnlyIn`; a row written before keeps its `requireMode` and is read as written. The routine editor sends `runsOnlyIn` and still gives a content action Free; its redesign is #1575's.

## Risks / Trade-offs

- The presentation class is rewritten around one base model; its presentation tests and the module's mode sites are the regression net, and the runtime's Pixoo scenarios run on the simulated device.
- Removing the empty-pause rule means a Pixoo in Free with nothing playing shows status and admits art; the owner's way to keep it dark is Screen off, which already refuses every moment.
- A device write from a mode change (Quiet brightness, the Work stop) inherits the module's uncertain-write hold; a mode command that completes `uncertain` leaves the saved mode in place and the next mode command writes fresh.
- Ownership, timing, privacy and recovery are unchanged: the module remains the only writer and state owner; policy applies at the mode command, never on a timer; no new personal data is stored; the saved mode and brightness keys are additive to the state table and an older module ignores them.

## Migration Plan

Moments setting: a value saved as `{overMonitor}` reads as `{overStatus}`, so the owner's choice carries over. Config: presentation version 1 keeps `mode` as an accepted, ignored member; `quietBrightness` is optional with its default. Store: the saved presentation's `mode` is ignored; the new `hubMode` and `rememberedBrightness` keys default to Free and absent; `emptyIntent` is left in place and unread. No installed configuration edit is needed; the installation window under #1576 may add `quietBrightness` and is otherwise the routine batch. Rollback is forward-only under the runtime's standing policy; the previous image and the stopped backup are retained.

## Open Questions

None blocking. The dashboard label for the status view settings ("Monitor" or "Status view") is #1575's.
