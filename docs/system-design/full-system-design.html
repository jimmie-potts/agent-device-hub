This is the September 19, 2026 design baseline. At that date, controller contracts, lifecycle validators and the reusable MCP library were delivered. The shared core, standalone host, playback service, general rules and shared dashboard were planned. Device repositories retain their own source and acceptance evidence.

Build locally. Keep the boundaries portable.

The first useful workflow is local Codex task monitoring and explicit control through the existing device services. General controls and Apple Music follow the basic local experience. Phone access, ambient voice and a dedicated server come later. BUNNY is a working name, not a repository or package rename.

These pages use the component approach from the Map Distributed System Design Docs task. Each design owns its detail; the overview connects the whole system. A document is a logical responsibility, not necessarily a separately deployed service.

  • 01 / OBSERVE

    Agent task state

    Host hooks → validated lifecycle metadata → one agent-state core → UI and device-monitor consumers. General automation is a later additional consumer.
  • 02 / REQUEST

    Explicit device control

    UI or MCP → common owning service → controller admission and queue → one physical writer. Receipts describe transport and uncertainty.
  • 03 / REACT

    Music and automation

    Windows connector → playback-state service → UI updates and approved rules → application actions → owning controllers.

Music has its own state owner. Rules may combine playback and task facts, but the agent-state core never becomes a general store for all assistant activity. Physical controllers receive supported actions and keep their own policy and queues.

Application & state / API-bunny

Application API

A common entry point for UI requests and approved actions, with behavior shared by MCP and automation.

At snapshot: PlannedApplication interface / REST API
Design referencesEVT-controllerCORE-agentCORE-playbackWRK-automation

Responsibility and resources

The future hub exposes configured devices, capabilities, task snapshots, monitor acknowledgment, playback state and accepted automation definitions. HTTP parses and authenticates requests; application services perform the operation. Internal modules can call those services directly. An API box does not imply an independent process.

ResourceOwnerBoundary
Device identity and supported controlsOwning device controllerConfigured IDs only; no client-supplied destination or raw protocol command.
Agent sessions and noticesCORE-agentActivity, attention, notice acknowledgment and freshness stay distinct.
Selected playback sessionCORE-playbackTrack, player state and supported commands.
Accepted rule definitionsWRK-automationInspect, enable, disable and revise approved recurring behavior.

Operation contract

HTTP route names, response codes and an OpenAPI document are not implemented. Hub #5 and the owning feature issues must freeze those details before clients depend on them. The following are use cases, not newly accepted endpoints.

Use caseInputResult
Read device stateRegistered target and authorized principalController snapshot with capabilities and observation age.
Request a device changeExisting controller request envelopeOwning controller receipt; queued and sent remain distinct.
Read or acknowledge task noticesSession/notice/consumer identityShared state change scoped to the intended monitor notice.
Read playback or request NextSelected player and advertised capabilityObserved state or bounded supported-operation outcome.
Enable a ruleInspected definition and explicit acceptanceSaved activation state; no implication that an action has executed.

Request execution

  1. Validate the request size, current authorization and fixed registered destination.
  2. Read required capability and concurrency facts. Preserve the controller-provided request identity, configuration revision and generation.
  3. Call the owning service. The controller reserves admission and serializes physical effects.
  4. Return its bounded result. A response lost after dispatch is uncertain; read state or explicitly reconcile the original identity. Do not manufacture a new identity and repeat the action.

Failure, transactions and limits

The hub cannot atomically commit its database and a physical-device effect. Each owner keeps its own transaction boundary. A multi-device action reports per-device outcomes; partial success does not become a global success. Hub ingress limits, authentication policy and operation timeouts remain Q-API in the decision register. Existing MCP limits are documented separately, not automatically inherited by a future HTTP API.

Verification and remaining work

  • Contract tests must cover unauthorized requests, unsupported capabilities, revision conflicts, overload and lost responses after dispatch.
  • Verify that UI, MCP and rule invocations reach the same owning operation with equivalent authorization and concurrency behavior.
  • No listener, endpoint, authentication deployment or physical effect is established by this document. See ADR-decisions.

Application & state / API-mcp

MCP interface

The implemented MCP library translates registered tools into calls to owning services. Its host controls the listener.

At snapshot: Source deliveredEmbedded protocol interface
Design referencesEVT-controller

Implemented boundary

packages/mcp exports an authenticated HTTP handler and typed service/tool registration. It opens no listener and starts no device writer. The owning application mounts its explicit /mcp route before body parsing. Standalone hub hosting and agent-status tools remain Hub #13.

Tools and calls

InterfaceBehaviorOwner
Generic device toolsList, status, power and brightness through immutable registered targets.createDeviceTools / bindDeviceTools
ControllerServicereadSnapshot(context) and submit(request, context).Controller admission, replay and queue
Application extensionsStrict input/output schemas and fixed registered targets. Existing Pixoo operations can retain their request_id semantics.Owning application
HTTP transportInitialized authenticated sessions; POST JSON responses; GET streams return 405.Host plus MCP handler

Security and resource bounds

Require a declared machine credential with current read/control and device scopes. Browser editing tokens are not machine credentials. Host and supplied Origin use explicit allowlists; incoming credentials are never forwarded to a remote controller. Defaults are 64 KiB request JSON, 1 MiB response JSON, 32 outstanding HTTP operations, 32 controller calls, 16 sessions and 64 devices. The package README owns all exact limits and protocol versions.

Cancellation and uncertainty

Cancellation before dispatch prevents submission. After dispatch, the owning controller retains the operation. Closing an MCP session or losing its response does not cancel backend playback. An unresolved operation continues occupying its capacity slot. Reconcile possible effects through the owner; the MCP layer does not automatically retry writes.

Evidence

The library includes fake-service and real loopback protocol/package tests. They are source evidence. Existing device-specific installed acceptance belongs to its original receipts; it does not establish future standalone BUNNY acceptance. New documentation checks do not rerun the product acceptance suite.

Application & state / CORE-agent

Shared agent-state core

Interprets agent observations once, so every task monitor receives the same task facts.

At snapshot: PlannedEmbeddable state module
Design referencesEVT-lifecycleDB-hubCH-feeds

Meaning of shared

Shared means common interpretation across qualified agent providers and device consumers. This core owns Codex/Claude task facts, not all BUNNY state. Music belongs to CORE-playback. One selected host owns the core at a time. The first host is planned inside Pixoo; a standalone BUNNY host later composes the same package.

State model

DimensionMeaningMust remain independent of
ActivityQualified evidence of agent work.Outstanding attention or a retained notice.
AttentionA continuing question or blocked input/approval.Agent permission decisions.
Notices and acknowledgmentRetained turn-ended notices with consumer-scoped acknowledgment.Successful work, readership or another consumer’s dismissal.
FreshnessAge of the latest attributable session evidence.Collector health, UI reads or browser activity.
Identity and relationshipsProvider/client/host/source/session, with evidenced turn and parent.Guessed parentage, path-derived identity or merged sessions.

Processing algorithm

  1. Accept only a validated lifecycle envelope. Derive identity and deduplication from the qualified contract.
  2. Apply the deterministic reducer with an injected clock. Retain uncertainty when turn/order evidence is unavailable.
  3. Commit current state, notices and selected labels through the active host storage boundary.
  4. Publish an immutable revised snapshot/change to bounded independent consumers. The reducer never commands a device.

Recovery and retention

Hub #3 requires observations to become uncertain after five minutes without session evidence. Restart restores previously active sessions as uncertain until fresh evidence arrives. Its diagnostic journal is bounded to 24 hours or 10,000 events, whichever comes first, while current state and notices remain. This bounded journal is not a permanent event-sourcing log.

Reject stale prior-turn changes and deduplicate retries. Retire only the intended notice on a new turn or acknowledgment. A stalled consumer cannot block ingestion or another consumer. Expired feed cursors recover from a current snapshot, without replaying old effects.

Verification and handoff

  • Use fake-clock reducer, privacy-canary, concurrent/reordered producer, interrupted-write, restart, retention and package-consumer tests.
  • Test two functioning device consumers beside a stalled third consumer.
  • Use Hub #30’s frozen early budgets as design input. Its later integrated acceptance is not a prerequisite for starting the core.
  • The future embedding API covers ingest, snapshots/subscriptions, acknowledgment, shutdown and migration. Exact storage schema and feed transport remain Q-DATA and Q-FEED.

Application & state / WRK-automation

Automation rules

Turns accepted events and conditions into explicit application actions without an open conversation.

At snapshot: PlannedRule evaluator / worker
Design referencesCORE-agentCORE-playbackDB-hubEVT-controller

Trigger and authority

The rule evaluator consumes meaningful state changes from their owners. It may consult both task and playback state. A proposed rule requires user acceptance before recurring behavior becomes active. The assistant may propose a definition, while evaluation runs independently of a model call. Basic agent monitoring remains usable before this general engine exists.

Example rule, not a schema

When the selected track changes, if Nanoleaf participates in music and current policy allows an interruption, request the selected lighting scene. This is an illustrative policy. Scene choice, rule syntax and conflict handling are not yet accepted wire contracts.

PartResponsibility
TriggerSubscribe to the relevant event category. Subscription is delivery selection, not action permission.
ConditionsRead required state with freshness requirements. Unknown facts require an explicit policy.
ActionInvoke the common application operation for a configured target.
Execution resultRecord per-target outcomes and uncertainty, preserving the controller identity.

Proposed execution and recovery

  1. Load enabled, accepted rule definitions and their versions. Match a qualified event.
  2. Evaluate conditions and device participation. Record why the rule matched, did not match or could not evaluate.
  3. Form a bounded action plan using configured IDs and supported capabilities.
  4. Dispatch through application services and retain the resulting controller identities/outcomes.
  5. On timeout or restart, reconcile ambiguous effects. Do not replay expired lighting effects or manufacture new write identities.

Decisions before implementation

Hub #45 must define durable execution identity, duplicate suppression, deadlines, loop prevention, cooldowns, scheduling, conflicting rules and crash recovery. The illustrative flow is a recommendation, not a promise of exactly-once processing. A database record cannot atomically guarantee a physical action. A broker, durable outbox or scheduling service has not been selected.

Verification

  • Cover disabled and unaccepted rules, stale conditions, duplicate triggers, source loss and a model outage.
  • Inject crashes before dispatch, after possible effects and before recording an outcome. Verify bounded recovery and no implicit repeated action.
  • Verify conflicting policies, manual device takeover and restoration under the owning controller.

The active host provides storage through a boundary owned by the application. No new database engine, schema migration or independently deployed database is selected here. For implemented schemas, open the controller database reference. Its 28 tables come from pinned Pixoo and Nanoleaf source DDL. They are not an implemented schema for the proposed BUNNY store.

Transactions and consistency

The core must commit a state transition and its durable notice changes coherently. Stable revisions identify committed snapshots. Publication after a committed update needs a recovery path so reconnecting clients can read authoritative state even if a change notification is lost. Exact transaction/API schema and migration code remain Q-DATA. No transaction spans a controller’s private database and BUNNY’s store.

Schema, indexes and examples

Entity names above are conceptual, not physical SQL tables. Implementation must define types, nullability, uniqueness, indexes, migration history and compatibility beside the owning code. Candidate indexes follow the actual session selector, notice/consumer identity and rule execution identity. Do not publish guessed migrations as an implemented database schema.

Use neutral fixture identifiers such as host-demo, session-demo and desk-display. Real credentials, private paths, prompts, transcripts and device addresses do not belong in fixtures or Git.

Migration and verification

  • Name the single migration executor and supported old/new versions before rollout. Test interrupted migration, restore and duplicate/concurrent operations.
  • A stopped-writer export/import must preserve identities, notices, revisions and selected labels when moving an existing shared owner.
  • The accepted fresh Nanoleaf Linux installation is a separate exception owned by Hub #43 and Nanoleaf #54/#55; it is not a generic rule to discard shared BUNNY state.

Contracts & data / EVT-lifecycle

Agent lifecycle contract

The strict shared metadata envelope used to qualify agent observations without transporting private task content.

At snapshot: Source deliveredVersioned event contract
Design referencesNo selected design dependency

Authoritative definition

The implemented contract is packages/lifecycle-contracts/schemas/lifecycle-v1.schema.json, with TypeScript/Python validators and a shared fixture corpus. API version is 1.0. The document and schema own the exact fields; this page explains their role.

Identity and envelope

The selector contains provider, client, hostId, sourceId and sessionId. Turn and parent relationships explicitly distinguish known and unknown evidence. Producer observation time is separate from occurrence time and ordering. A retry retains its original validated envelope and observation time. Native turn IDs and wall-clock arrival do not prove order.

Representative observations

KindMeaning
turn.started / activity.observedNew-turn or work evidence, independent of attention.
question.continuing / attention.input / attention.approvalContinuing questions and blocked attention; no permission decision.
turn.ended / turn.interruptedNotice or interruption; neither proves successful work or readership.
notice.acknowledged / read.observedConsumer-scoped acknowledgment versus separately qualified optional read evidence.
evidence.unavailableUnsupported, inaccessible, missing, ambiguous or lost evidence.

Privacy, compatibility and bounds

Construct an allowlist before serialization. No prompts, transcripts, tool content, automatic titles, credentials or private paths. Closed objects reject unknown fields; an envelope is bounded to 8192 UTF-8 JSON bytes, depth 8 and 256 visited values. These admission bounds are not latency measurements. Validate source provenance as well as schema shape. New fields require an explicitly supported API version.

Processing and verification

Use the shared native/content deduplication functions; do not hash excluded input. Content identity can collapse indistinguishable observations and does not prove exactly-once history. Both language consumers execute the same fixture identities and expected hashes. The validator is delivered; the runtime reducer and installed producer qualification remain separate.

Contracts & data / EVT-controller

Controller command contract

A shared vocabulary for capabilities, safe command admission, receipts and truthful device observations.

At snapshot: Source deliveredVersioned command / observation contract
Design referencesNo selected design dependency

Wire authority

Controller API 1.0 is defined by packages/contracts and the controller-contract document. Capability declarations and pure reference consumers are implemented. Each runtime still owns adoption and enforcement; a passing reference fixture is not proof of a deployed endpoint.

Request and outcome

ObjectImportant fieldsMeaning
RequestcontrollerId, deviceId, requestId, expectedConfigurationRevision, expectedGeneration, commandServer-issued identity plus explicit concurrency expectations.
ReceiptrequestId, configurationRevision, generation, outcome, priorEffectsOutcomes: queued, sent, failed, partially-applied, uncertain, cancelled.
SnapshotCapabilities, nextRequestId, cursor, health, desired/pending/outcome/observationA read never creates a command or refreshes evidence.

Admission and physical execution

  1. Authenticate and authorize before replay lookup. Reject invalid targets, schema violations and resource overflow before admission as specified.
  2. An identical retained identity/body returns its original result. Changed bodies conflict; expired identities never execute as new work.
  3. Atomically reserve admission and check expected revision/generation.
  4. Check generation again before queued effects. One designated writer performs the physical operation.
  5. Retain truthful prior effects and uncertainty. A sent result means successful transport, not visible light or pixels.

Supported capability boundary

Power, brightness, scenes, zones, media, preview and device modes are explicitly advertised. Ordinary lights do not acquire a pixel-buffer API. Current v1 includes typed commands such as power.set, brightness.set and scene.activate. Apple Music controls and now-playing render requests need their own qualified application integration; they are not arbitrary new fields in this closed schema.

Recovery and verification

Exercise the shared replay, concurrency, expired-cursor, stale-generation, authorization, privacy and uncertainty fixtures in each real owning service. Default replay retention is 256 completed receipts in the reference v1 contract. Recovery uses current snapshots and the original request identity, with no automatic new-identity retry.

Contracts & data / CH-feeds

State feeds and subscriptions

Distributes current facts to UI and policy consumers without making every subscriber a state owner.

At snapshot: PlannedLogical message channels
Design referencesEVT-lifecycleEVT-playback

Topology

Logical feedProducerConsumers
Interpreted agent stateCORE-agentUI, registered device-monitor consumers and future rules.
Interpreted playback state / transitionsCORE-playbackUI and approved music policy / future rules.
Controller observationsEach owning device controllerApplication read model and UI.

Transport is a separate choice

These are logical subscriptions. In-process callbacks can serve an embedded consumer; cross-process consumers need a qualified authenticated feed. A message broker, topic product, consumer group and permanent event log have not been selected. Do not mistake the Observer pattern for a requirement to deploy messaging infrastructure. Agent and playback transport details remain Q-FEED.

Delivery and overload

The agent core exposes immutable revisioned snapshots and bounded independent consumer delivery/history. A stalled consumer cannot block others or extend a provider hook. Bound bytes, queued changes and processing time. Expired cursors resynchronize from the current snapshot. Exact transport acknowledgment and retention semantics must be specified before implementation; do not claim at-least-once or exactly-once delivery from an in-memory subscription.

Actions and replay

A state feed carries facts. Rules decide whether facts cause an action; controllers receive supported commands through owning services. Snapshot replay does not replay expired physical effects. Automatic agent-monitor consumers retain their existing presentation policy and do not depend on the future general rules engine.

Verification

  • Verify two active consumers with a stalled third; bounded memory and independent progress are required.
  • Test disconnect, expired cursor, restart, authorization revocation and missing source evidence.
  • Distinguish feed health and delivery from the age of the underlying task, player or device observation.

  3. Perform the bounded handoff to the selected state owner, preserving stable source identity.

Placement and migration

The host hook remains beside the agent runtime even if BUNNY later runs in Docker or kind. Containers stay behind the bounded handoff. Only one selected ingestion path updates a session. Drop new observations on saturation as required by the contract, retain a bounded loss indicator and expose missing evidence later. Do not serialize private provider input into errors. Use the early Linux budget artifact for process/queue/deadline design; installed hooks require real-client checks under Hub #8.
