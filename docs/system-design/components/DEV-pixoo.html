Hosts & devices / DEV-pixoo

Pixoo controller

Owns media, playback, rendering and the serialized display writer; shared monitoring is a separate integration.

At snapshot: Mixed evidencePhysical-device controller
Design referencesEVT-controllerCH-feeds

Current baseline

Pixoo source at 9f1c0ec7 includes the media library, reference-safe deletion, playlist playback, HTTP API and optional MCP endpoint. Shared lifecycle vocabulary/consumer requirements exist; shared runtime monitoring and its UI remain separate work. Existing local acceptance receipts retain their original scope.

Browse the source-pinned Pixoo HTTP API, media library tables and separate ownership-lock table. These offline references do not select a running service or contact a device.

Ownership

Pixoo privately owns originals, referenced renditions, SQLite library state, playback recovery and physical operation serialization. B.U.N.N.Y. calls the owning API. It never writes Pixoo’s database or bypasses its queue. The first shared agent core is planned for embedding in the existing backend; only that selected host owns shared task state.

Monitor, media and music

Preserve simulator startup and explicit Monitor/Media intent. A monitor acknowledgment affects only its intended notice. A now-playing card needs a qualified render/application operation and participation policy; it is not automatically an existing playlist or an arbitrary command field. Maintain interruption, manual takeover and restoration behavior.

Failure and verification

  • Unavailable hardware must not block state ingestion or other controllers. Keep pending, sent and uncertain effects distinguishable.
  • Test media retention and recovery with a simulator and synthetic files. Separately verify transport, actual pixels, timing and restoration.
  • Existing uniform-cadence evidence does not establish a smooth audio visualizer or frame-perfect future music effects.
