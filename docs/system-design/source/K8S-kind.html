Purpose and open choices

The template task used kind as its local-development context. BUNNY keeps that as an optional design track; it does not replace the accepted Docker-on-PC direction or become a prerequisite for local device control. Cluster version, node image digest, container runtime, topology and namespace are not selected.

Host and LAN boundary

Windows player access and host agent triggers stay outside the cluster behind explicit adapters. Loopback inside a container/pod refers to that environment, so host access needs a selected route and authorization. No router/firewall changes, public ingress or real-device tests are implied.

Bootstrap and reset runbook status

There is no approved kind manifest or create/delete command for BUNNY. Q-KIND requires the owner to select versions, routes, storage survival and fake-only configuration before a runnable runbook is added. Document deletion and restore consequences before using a real data volume.

Verification

Record cluster/context, image digests, workload revision and source configuration for each run. Prove readiness, service access, restart and storage recovery with synthetic state. Passing those checks still leaves Windows-session access, LAN transport and visible-device acceptance unproven.
