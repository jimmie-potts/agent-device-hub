Provider hooks

allowlisted metadata · fail-open · source · setup SDK

The setup SDK installs one producer per qualified source. Each hook normalizes allowlisted metadata, sends one bounded request to the selected owner within a 2.9-second deadline, and returns silently on invalid input, saturation or an offline owner. It never changes agent permissions or waits for a device.

Hub HTTP routes

monitor · controllers · mcp · loopback · bearer · Linux hub process (apps/hub) · source; installation separate

One numeric-loopback listener authenticates every request before replay. Monitor routes: GET /api/monitor/v1/sessions, POST /api/monitor/v1/events, POST /api/monitor/v1/commands and the SSE feed GET /api/monitor/v1/changes. Host routes: GET /api/hub/v1/health and /api/hub/v1/authority. Dashboard context: GET /api/dashboard/v1/context. Controller routes: /api/controllers/v1/:id/snapshot, /commands and /integration/{snapshot,commands,receipt,cancel}. Optional /mcp. Limits: 32 concurrent requests, 16 streams, three seconds per request.

WALKTHROUGH · ONE OBSERVATION, NO DEVICE EXPERIMENT

One agent observation, from hook to device.

One provider observation travels from a fail-open hook to the hub, is committed once as a new revision, is published as a revision pointer, and is projected by the owning controller onto its device through that controller's own queue. The alternative shows reconnecting after an interruption without replay.

  1. A provider hook builds the allowlisted envelope and posts it once to /api/monitor/v1/events with its ingest credential. The hub answers applied, duplicate, stale or a fixed rejection code. If the hub is slow or down the hook still returns within 2.9 seconds; the observation is dropped, never queued for later delivery.

    1. Provider hook → Hub HTTP routes POST /events: allowlisted metadata, ingest bearer prompts, transcripts, tool content and titles never leave the host
    2. Hub HTTP routes → Agent-state core ingest(envelope)
    3. Hub HTTP routes → Provider hook applied · duplicate · stale — within the hook bound the hook also returns when the hub is down

Design baseline notes, 19 September 2026: scope, recorded evidence, workflows, module placement and quality targets
These notes describe the September 19, 2026 design baseline. At that date, controller contracts, lifecycle validators and the reusable MCP library were delivered. The shared core, standalone host, playback service, general rules and shared dashboard were planned. Device repositories retain their own source and acceptance evidence. The map above is newer and pins its own source revisions.

Build locally. Keep the boundaries portable.

The first useful workflow is local Codex task monitoring and explicit control through the existing device services. General controls and Apple Music follow the basic local experience. Phone access, ambient voice and a dedicated server come later. BUNNY is a working name, not a repository or package rename.

These pages use the component approach from the Map Distributed System Design Docs task. Each design owns its detail; the overview connects the whole system. A document is a logical responsibility, not necessarily a separately deployed service.

  • 01 / OBSERVE

    Agent task state

    Host hooks → validated lifecycle metadata → one agent-state core → UI and device-monitor consumers. General automation is a later additional consumer.
  • 02 / REQUEST

    Explicit device control

    UI or MCP → common owning service → controller admission and queue → one physical writer. Receipts describe transport and uncertainty.
  • 03 / REACT

    Music and automation

    Windows connector → playback-state service → UI updates and approved rules → application actions → owning controllers.

Music has its own state owner. Rules may combine playback and task facts, but the agent-state core never becomes a general store for all assistant activity. Physical controllers receive supported actions and keep their own policy and queues.
